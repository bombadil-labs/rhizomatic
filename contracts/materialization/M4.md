# M4 cumulative acceptance: build notes

[SPEC-16](../../spec/16-materialization.md) MR-23 owns the tower and evidence requirements, and
[CI.md](CI.md) names the harness failure proofs. This file records how the nine M4 cases execute.
It is a builder's note, not a review acceptance. The case ledger is [M4-CASES.json](M4-CASES.json).

## Slice M4a: harness probes and the cumulative gate

M4 adds no witness behavior. It checks the M1, M2 and M3 evidence as one body, from the bundles
that one CI run retains, and it adds the probes the milestone runners did not yet carry.

**The cumulative checker.** `tools/check-materialization-m4.mjs` reads the retained M1, M2 and M3
bundles and checks:

- every retained artifact still hashes to its recorded digest;
- every required scenario of each milestone has three validated mixed plans, with repeats
  reported, and each tower's replay equals its first run byte for byte;
- both fixed routes of each milestone ran for every required scenario;
- the retained outputs equal the shared goldens: M1 envelopes, M2 final readbacks, and every M3
  restore and read outcome against the lifecycle schedule;
- against each milestone's real capability manifest, seven changes refuse at the gate: a stage
  advertised without executed cases, an upper witness advertising a stage, a replay assigning a
  stage to Elixir, a deleted Rust port that a fixed route needs, a missing recorded build, a stale
  build and a modified plan; Elixir and Haskell stay below this level in every manifest;
- all three `cmd_gather_resolve_fresh` towers rewritten to report height 99 where the fixture
  specifies 42 still agree with each other, and the independent oracle turns all three red;
- the M3 runner replays a retained scenario without a seed reroll: the intact bundle
  reproduces, and a bundle with one changed recorded signature refuses with `retained exact
  replay`;
- each runner carries its named harness failure proofs.

**New M3 runner probes.** A producer exports a valid image and the consumer receives it with a
trailing byte or one flipped appearance-signature byte. Restore refuses `invalid-control` and
readback refuses `invalid-evidence`, in both producer and consumer directions; each record names
the producer, the consumer, the edge and the change. For isolation, tower 0 runs and then its
control image and source state change; towers 1 and 2 reproduce their recorded results in fresh
directories, and a tower pointed at tower 0's directory is detected. The runner also gains the
unsupported-stage and missing-stage-evidence negatives the M1 and M2 runners carry, and an
`M3_ONLY` filter that the replay probe uses.

**The existing gates.** The `materialization-m4` CI job needs the TypeScript, Rust, Haskell,
Elixir, command, M1, M2 and M3 jobs of the same run, downloads their bundles, and requires every
one of them to have succeeded on the checked-out commit. A local run reports this case as
`not-run-locally`; it cannot manufacture CI results.

## Slice M4b: the lifecycle resource baseline

The M2 report already measures the nested Bed fixture and the source sweep through capture,
gather, readback and resolve. M4b adds the lifecycle phases over the same sweep.

**The sweep.** `tools/measure-materialization-lifecycle.mjs` asks the vector generator for one
fixture per size: 0, 128, 1024, 4096 and 4097 selected source appearances. The generator builds
each fixture with the same code paths that produce the committed lifecycle vectors, and the run
checks that the committed vectors do not change. For each size up to 4096, the fixture has an
install, an equal-size replacement (from 128 up), a fresh restore and a fresh read. At 4097 the
install refuses `resource-limit`.

**The hosts.** Each witness has a measurement host. Every step boots a new endpoint over an
in-memory store that holds the step's stored image, so each phase is a cold restart from durable
bytes. The host checks that the outcome and the stored image equal the generator's goldens. The
Rust host compares canonical claim bytes, ids and signatures. A counter goes into each witness's
exact strict signature verifier in a disposable build copy; no other code changes.

**What the report records.** For each step: delivery, control-before, control-after and result
bytes; boot and phase wall time; strict signature verifications; source-current checks; and peak
process memory for each size. The runner requires equal phase lists, statuses and byte lengths
between the witnesses. The report also names the shared boundary vectors. Each pair is one limit
at its exact value and one value below it: delivery bytes (with signed carrier overhead),
artifact bytes and request pointers. It also names four over-only limits and the four lifecycle
over-limit steps. Both witness suites already execute all of these.

**What the checker adds.** `tools/check-materialization-m4.mjs` reads both reports. It requires
the M2 rows for the nested fixture and the sweep, the lifecycle rows for every size, agreement of
byte accounting, a finite time and an integer verification count for every phase, and refusal at
4097 with zero source checks.

**No thresholds.** The report states numbers only. A slow phase is a measurement, not a failure.

**Deferred to M5.** Journal-backed published Plant and Bed counts and bytes, and the native or
portable route choice. The lifecycle sweep does not run over the nested Bed fixture; the M2 report
holds that fixture's batch phases.

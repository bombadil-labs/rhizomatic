# M3 maintained lifecycle: build notes

[SPEC-16](../../spec/16-materialization.md) MR-13 to MR-18 own the behavior. This file records
the ports, the decisions the spec left open, and the evidence as the milestone is built. It is a
builder's note, not a review acceptance.

## Slice A: representation and durable seam

| Owner | TypeScript | Rust | Contract |
| --- | --- | --- | --- |
| reactor | `src/reactor/materialization-control.ts` | `materialization_control.rs` | `rhizomatic.materialization-control/1` |
| storage | `src/storage/materialization-store.ts` | `materialization_store.rs` | `rhizomatic.materialization/1/control-store` |
| federation | `src/federation/materialization-control.ts` | `materialization_peer.rs` | facade re-exports only |
| command-data | `materialization-codec.ts` | `materialization_data.rs` | `rhizomatic.materialization/1/description` |

The reactor module holds the normalized selection (each entry names the support it keeps
reachable), derives the flat image, encodes and strictly decodes the canonical image, names the
external revision, and plans the four control transitions as a pure function. It never decodes an
act, never signs, and never touches a store. The storage trait is initialize, read and
compare-and-set over opaque bytes with the four MR-15 outcomes. Command reaches both through the
federation facade, which keeps the declared owner graph.

Decisions recorded in `spec/16-materialization.ERRATA.md`:

- E2: a control image carries at most `registrations × (definitions + 4)` appearance records,
  checked before the array is walked; the reactor treats support as opaque bytes and binds a
  retired entry to exactly one record, which command ties to `entry.transition` on restore.

Shared evidence:

- `vectors/materialization/control-image.json`: 3 positive images and 21 hostile images from an
  independent generator that imports no codec. Both witnesses decode, re-encode byte-exact, name the
  revision, and refuse each hostile image with the same code. The planner reproduces the shared
  images from an empty selection through install, install and retire.
- `vectors/materialization/command-descriptions.json`: the six lifecycle requests, all eight
  operation declarations with their effects, a registration descriptor, an install and a retire
  state act, and a control-image carrier, from the Python oracle.

## Slice B: the six verbs, the CAS and readback

| Owner | TypeScript | Rust |
| --- | --- | --- |
| command | `src/command/materialization-lifecycle.ts` | `materialization_lifecycle.rs` |
| command | `src/command/materialization-result.ts` (MR-20) | `materialization_result.rs` |
| command | `src/command/materialization-preflight.ts` | `materialization_command.rs` |

Release B boots name the control store explicitly (`controlStore` in TypeScript,
`boot_maintained` in Rust); a release-A boot still refuses every lifecycle verb at stage 3. The
lifecycle module reads and classifies the image at stage 5 through one pure reader
(`classifyMaterializationControl` / `classify_control`), checks the explicit source at stage 6 and
the stored or supplied program at stage 7, computes every root and the prospective transition at
stage 8, and performs the CAS at stage 9. The preflight projection covers install's supplied
source and program; every other maintained check depends on the control image and stays
unsupported in preflight (MR-21).

Readback (MR-20) now reads all eight completed body kinds, every refused code including the
nine M3 codes, and both indeterminate bodies. A maintained body is `verified-structure` on its
own. It becomes `verified-context` only when the caller supplies both the request and the
control image the body names: the image's revision and generation must equal the body's, the
named entry's latest transition must equal `transition`, its status must agree with the verb, and
a serving body's Basis scalars, pins, binding, program closure and complete root partition must
equal the stored descriptor and entry. Restore selections must equal the image entries exactly.
A supplied capture/snapshot pair still upgrades `sourceCommitments` to `commitments-verified` by
recomputation against the Basis, as for gather. Nothing in readback executes a program.

Shared evidence:

- `vectors/materialization/lifecycle.json`: twenty steps, each booting a fresh endpoint from an
  explicit control image. Seven complete (install, read, advance-time, replace-source, retire,
  restore of a retired image, restore of the empty image) and thirteen refuse by category. Both
  witnesses sign byte-equal outcomes and leave byte-equal images.
- Readback of every step in both witnesses: the body bytes, the structure/context classification,
  the demotion when the pre-CAS image or another request is supplied, and the refusal of a forged
  body missing one root result.
- `contracts/materialization/M3-CASES.json` allocates the 33 required cases and 6 variants.
  `tools/check-materialization-m3-acceptance.mjs` runs both witnesses, checks the receipts and
  the allocation, and writes `artifacts/materialization-m3/`. States after slice B: 5 executed,
  9 partial, 25 specified. Partial and specified cases name what remains.

Decisions recorded in `spec/16-materialization.ERRATA.md`: E3 (three small lifecycle decisions)
and E4 (the readback linkage rule above).

## Slice C1: durable hosts, fault points and mixed towers

Both fixture hosts (`implementations/ts/tools/materialization-fixture.ts`,
`implementations/rust/examples/materialization_fixture.rs`) gain a host-private durable control
store: one JSON document per receiver and configuration under a directory, replaced whole by
rename, holding the revision the endpoint named beside the image bytes. The layout is the same
in both hosts, so either witness restores a directory the other wrote. The store never decodes
an image. The hosts add five stages from `TOWERS.json`: control-execute, control-export,
control-restore, control-read and control-result, plus a verb-generic construct.

Every stage is a fresh process. The executing stage seeds its directory from a schedule step's
initial image, runs the step, and the exporting stage reads the directory back. The restoring
stage writes only the exported bytes and revision into a second fresh directory and runs the
restore verb there; the reading stage runs a read on that directory; the result stage reads the
read outcome back with the exported image as control linkage.

Faults name one MR-18 point each and are injected by the host, never by the endpoint:
crash-before-cas and crash-after-cas end the process, unconfirmed-absent and unconfirmed-present
answer committed-unconfirmed with and without the durable write, rejected answers rejected,
post-cas-result fails the named post-CAS hook, and sign-failure fails the outcome signature after
the transition signed. After a fault the directory is the oracle: the exporting stage must find
exactly the image the schedule names, and a crashed host answers nothing.

`tools/check-materialization-m3-towers.mjs` runs three required tower scenarios
(ctl_cross_witness_restore, ctl_uncertain_present, ctl_retired_restart) in both fixed directions
and in three seeded mixed plans each with exact replay, and eight fault schedules in both fixed
directions. Retained replay re-checks a prior run. `M3-TOWERS.json` and `M3-CAPABILITIES.json`
land beside the acceptance artifacts. The schedule grew by five steps for the images the towers
restore and read (restore_installed, restore_advanced, restore_replaced, read_advanced,
read_replaced).

The packet files `TOWERS.json` and `BOUNDARIES.json` stay frozen specifications; the
executed capability record lives in the artifacts, as for M2.

## Slice C2: more sources and descriptors in the shared schedule

The schedule grew to 47 steps. Each new step still boots a fresh endpoint from an explicit
image and keeps the plant program unless it says otherwise:

- Two more sources from the batch oracles that share the program (`negated`, `restored`), the
  same rows under a new authority (`same_rows_changed_authority`), an equal-count replacement
  with height 87, and a physical removal of the height fact. Replace-source and read steps pin
  the new revisions, transitions, images and root results; stale reads refuse `source-changed`.
- A second descriptor on the same source (root `item:moss`), replacing only the fern source,
  reading both, and restoring two selections. The generation is global, the selections are
  independent.
- A descriptor that expires at 1200 retires at 1500 with no source grant at all.
- After the fern descriptor retires, a new descriptor selects the later-signed definitions at
  definition-at 1500; the image holds the retired terminal transition beside the new support.
- A read after the stored authority expires refuses `invalid-source` at 2500.

A step may name its own `source`, `receivedAt` or `noGrant`; both test harnesses and both
fixture hosts honor them. Every step also checks that no delivered snapshot payload is in the
stored image (MR-14). The towers gained the two-writers race: the host lands another writer's
image between its read and its CAS, the endpoint refuses `write-conflict`, and the directory
holds the other writer's image.

States after slice C2: 25 executed, 6 partial, 8 specified of 33 cases and 6 variants.

## Review round 1

The first independent review of 17032db found seven defects in slices A to C2: two witness
divergences (UTF-16 versus UTF-8 root order; untyped roots and aliases), four correctness gaps
(no administrator check, no roots limit, no capture-basis check on restore, readback not
linking a mutating request to its transition or its serving time) and one precedence error
(expected-source before the other stage-6 checks). Each is fixed in both witnesses and pinned
by a shared step; ERRATA E5 records the decisions. The schedule has 60 steps, every step names
its preflight projection, and a step may boot another configuration of the receiver.

## Review round 2

The second independent review of 1c81d7f confirmed the seven fixes and found four more
defects: a root partition compare that joined roots by NUL and so accepted a single forged
result, a restore that trusted a signed image's pins without checking them against the retained
acts, a stored capture basis read as three fields instead of the complete MR-10 basis, and a
readback that did not link an install or replacement request to the capture the image selected.
Each is fixed in both witnesses; ERRATA E6 records the decisions. The schedule has 62 steps
(`restore_bad_hyperschema_pin`, `restore_truncated_capture_basis`), and the hostile-context
tests in both witnesses pin the two readback findings.

## Review round 3

The third independent review of 25a1c22 confirmed the four round-2 fixes and found two more
defects in the new capture-basis path: the decoder did not enforce the snapshot's inventory
rules (operand peers against the components table, distinct appearance keys, recomputed
membership and appearance digests), and the classifier did not compare the capture's signed
claims to the observation its basis names. Both are fixed in both witnesses; ERRATA E7
records the decisions. The schedule has 65 steps (`restore_capture_observation_mismatch`,
`restore_capture_foreign_peer`, `restore_capture_wrong_appearance`).

## Slice C3a: validity, shared-basis limits, strict control, unrelated binding

The schedule grew to 89 steps. Each new step still boots a fresh endpoint from an explicit
image; a local oracle builds gather and resolve bodies for any source, selected rows and time
with the batch encoders, so no batch fixture was added.

- Validity (ctl_validity_advance): a height fact valid on [100, 200) installs at 99, advances
  through 100, 199, 200 and 2100 with height absent, 42, 42, absent, absent; a decrease to 150
  is `time-regression` with no write; the expiring descriptor refuses `invalid-definition` for
  read and for advance-time at serving time 1500 with the selection unchanged.
- Shared-basis limits (ctl_shared_basis_limits): two-root and 64-root descriptors with one fact
  per root install and read under entries and nodes lowered to 1, with one Basis per body. A
  body limit just below the 64-root body refuses install, replace-source and advance-time
  `resource-limit` before CAS; an image limit just below a 200-alias descriptor's image refuses
  install the same way. The generator checks each limit sits above every other artifact.
- Strict control (ctl_control_strict): unreachable support, a retired-only image with old
  support injected, retired scalars changed under the unchanged terminal transition, and an
  authority whose signed interval is malformed each refuse `invalid-control` at stage 5. A
  snapshot carrier with an unknown top-level key is `precondition-failed` with a wrong
  expected-control and `invalid-source` with the right one.
- The unrelated-binding variant boots a configuration that selects the descriptor's binding and
  an expired second binding, with no source grant; retire and restore complete.

States after slice C3a: 24 executed, 2 partial, 7 specified of 33 cases; 5 of 6 variants
executed. ERRATA E8 records the readings.

Not yet built (slice C3b and C3c): restore with a destroyed source provider, the source races

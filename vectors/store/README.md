# Store vectors

These files pin the store interface of [SPEC-18](../../spec/18-store.PROPOSAL.md) (proposal),
slice 1: peers and postures, append, point reads, the scope query, purge, snapshots and export.
This page is the format contract. An implementer needs this page, SPEC-18 §4 and the two JSON
files, and no witness source.

| File | Contents |
|---|---|
| `scripts.json` | Operation scripts. Each step names its expected ids, report or refusal. |
| `scope.json` | The trim lemma (SPEC-18 §4.3): one holding set, then scope cases. |

Both files are generated by `implementations/ts/tools/gen-store-vectors.ts` (`npm run gen-vectors`).
Expectations come from a model that scans plain lists, not from a store. The memory store must
pass the documents before the generator writes them. CI regenerates the files and compares bytes.

A conformance run covers **both** files. `scripts.json` alone does not hold a store to the exact
upper bound of a scope (§1.4.1); only `scope.json` does. A runner's default is both.

## 1. What a witness must provide

A witness runs the vectors against a **store**. The operations below are SPEC-18 §4 in neutral
form. Names are the vectors' names; a witness spells them in its own idiom. A Rust store is
synchronous; "refuses with `code`" means it returns an error value that carries that code.

**A store owns what it holds; no caller holds a reference into it.** A store keeps its own copy
of every delta, signature and arrival record it is given. Changing a value after it was appended
changes nothing in the store. Changing a value a store returned changes nothing in the store, for
this peer or any other. This holds for every part of a delta, a bytes payload included: a copy
must not share memory with what the caller holds. It holds for the store's profile too: the
profile a caller reads is not the object the store decides by, and no caller can reach that
object. A store keeps only the canonical fields of a delta's claims (SPEC-1 §2); anything else a
caller attached is not stored and not served.

**A store never converts what it is given.** It takes a value only when the value has the type
its position requires, and refuses every other value. A bytes payload must be the witness's byte
array type; a buffer the payload could be built from, a number, a list of numbers and an array of
another element size are refused, not turned into bytes. The claims a store hashes are the claims
it keeps: it checks and hashes its own copy, so nothing the caller does between the check and the
copy can put other claims under an id. The refusal is `invalid-admission` in `append` and
`invalid-request` everywhere else. A witness whose types cannot hold a wrong value satisfies the
rule by its types. No vector reaches this rule (§5).

**Handles are owned.** A peer handle and a snapshot stay usable for as long as the store is open.
Opening a peer again does not end an older handle of that peer: both are views of one peer, and
each sees what the other wrote. So `snapshot-moved` and `snapshot-released` are refusals at run
time in every witness, never something a type system rules out.

### 1.1 Values

- **Id**: a delta's content address, lowercase hex.
- **Delta**: `{id, claims, sig?}`. Two deltas with one id and different `sig` are two
  **appearances** of one id.
- **Arrival record** (SPEC-6 vNext §3): `{id, at, sequence, transfer, sender}`.
  - `sequence` and `transfer` are integers from 1 to 2^53 − 1 (9007199254740991), in every
    witness. JSON carries both bounds exactly.
  - `at` is a finite number of milliseconds. It may be fractional: SPEC-6 vNext §3 takes it from
    the receiver's clock and does not restrict it to integers.
  - `sender` is a non-empty string.
- **Signature**: when present, exactly 128 lowercase hexadecimal characters (SPEC-1 §5, the form
  the `l0-delta` signed vectors use). The store checks the form, never the signature itself.
- **Held delta**: a delta with the arrival record of the peer that holds it.
- **Head**: an opaque non-empty string, or null when the peer never committed an append. Two
  heads are equal when they are the same string, byte for byte. No case folding, no trimming.
  Null is not the empty string: an `expectedHead` of `""` never matches.
- **Revision**: a value with a total order inside one peer. The vectors use only "equal" and
  "greater".
- **Order.** Every list of ids, deltas or arrival records a store returns is ascending by the
  UTF-8 bytes of the id, with no id twice. Peer ids are listed ascending the same way.

### 1.2 Store

| Operation | Result |
|---|---|
| `profile` | The store's declared profile (§1.6). |
| `createPeer(peerId, erasure)` | A peer handle. `erasure` is the posture: `proven` or `unproven`. |
| `peer(peerId)` | A handle to an existing peer. |
| `admin.peers()` | Every peer id. |
| `admin.peer(peerId).ids()` | The ids that peer holds. |
| `admin.peer(peerId).deltas()` | The same members, each as that peer admitted it. |
| `admin.storedIds()` | Every id the store keeps bytes for, once each, whichever peers hold it. |

A peer handle exposes its posture and the store's erasure class recorded at creation. A new peer
holds nothing: its head is null and its count is 0. Its revision is whatever the store starts at;
the first commit is greater.

Refusals:

| Code | When |
|---|---|
| `posture-refused` | `createPeer` with posture `proven` on a store whose erasure class is not `proven`. Nothing is created. |
| `peer-exists` | `createPeer` for an id that exists. |
| `peer-absent` | `peer`, or an `admin.peer(...)` listing, for an id that does not exist. `peer` never creates. |
| `invalid-request` | `createPeer` with an empty peer id, or with no posture or a value that is not a posture. |

When `createPeer` has two causes at once (posture `proven` on a store that is not `proven`, for an
id that exists), `posture-refused` and `peer-exists` both conform.

**`invalid-request`, the closed list for slice 1:**

1. `createPeer` with an empty peer id, or without one of the two postures.
2. `scope` with a `timestampAtMost` that is not a finite number.
3. `scope` with an `arrivalAtMost` that is not an integer from 0 to 2^53 − 1. (0 is legal and
   selects nothing, because sequences start at 1.)
4. A requirement name at open that is not in the store's list of requirement names.
5. The synchronous source over a fetched scope (`scopeSource`), given a member whose id does not
   recompute from its claims, or a member with a value that is not of its type. The first
   appearance of an id is kept and checked; a repeated id is not examined. A refused call adds
   nothing: the source is unchanged, or is not built. The source owns its members as a store
   does: it copies them in without converting, and what it returns cannot be used to change it.
   Building the source costs the total size of its members: N members at one entity, or N
   negations of one delta, cost N steps and not N². Each witness has a rail for this (§5, "Cost").
6. In a dynamically typed witness only: a request with a value that is not of its type. A list of
   ids or entities that is not a list of strings, an anchor that is not an object with a kind, a
   `createPeer` without options. A typed witness cannot receive one.
7. In a dynamically typed witness only: an optional object field that is present and is not a
   plain object. "Absent" means the field is not given (in TypeScript, `undefined`); then it means
   none. Any other value is refused, also `null`, a list, a number, a string, a boolean and a
   function: a store never reads such a value as an empty object. Slice 1 has two such fields:
   the `pushdown` of `scope`, and the options of opening a store (§5, "`openStore`").

A witness whose types make a case unrepresentable (a missing posture, a NaN in an integer field)
satisfies it. Vectors cover the empty peer id and the three `arrivalAtMost` refusals. JSON cannot
carry NaN or an infinity, so a non-finite `timestampAtMost` or `at` is a unit test in each witness.

### 1.3 Peer

**`read()`** returns a snapshot at the peer's current revision.

**`append({expectedHead, nextHead, frame, added})`**, where `added` is a list of held deltas.
The checks:

- **(a) Shape of the call.** `nextHead` is empty: refuse `invalid-admission`. `frame` is not null
  and the profile's `journal` capability is false: refuse `capability-absent`. In a dynamically
  typed witness, a call that is not an object, or a `nextHead` that is not a string, is refused
  `invalid-admission` here; an `added` that is not a list is refused in (c), after the head.
- **(b) The head.** The peer's head is not equal to `expectedHead`: answer `conflict`. Nothing
  changes.
- **(c) The batch.** Walk `added` in order. For each entry:
  1. The entry, its delta, its claims, its signature or its arrival record holds a value that is
     not of its type (a dynamically typed witness only); or the id does not recompute from the
     claims (SPEC-1 §4): refuse `invalid-admission`.
  2. A signature is present and is not 128 lowercase hex characters: refuse `invalid-admission`.
  3. The arrival record's `id` is not the delta's id; or `sequence` or `transfer` is not an
     integer from 1 to 2^53 − 1; or `at` is not a finite number; or `sender` is empty: refuse
     `invalid-admission`.
  4. The peer already holds the id, or an earlier entry of this batch has it: skip the entry.
     The peer keeps the appearance and the arrival record it already has; this entry's signature
     and arrival record are ignored.
  5. `sequence` is not greater than the largest sequence this peer ever committed, or equals the
     sequence of an earlier **new** entry of this batch: refuse `invalid-admission`. A skipped
     entry (step 4) spends no sequence: its sequence is not compared with anything, a later new
     entry may carry the same number, and it does not raise the peer's largest committed sequence.
     This holds for both kinds of skipped entry, and a vector pins each: an entry whose id the
     peer held before the batch, and a repeat of an id inside the batch.
  6. Otherwise the entry is **new**.
- **(d) Commit**, all together: the peer holds every new delta with its arrival record and
  signature; the head becomes `nextHead`. Answer `committed` with the new ids (ascending) and the
  revision.

**Order.** Two orders are pinned by vector:

- (b) comes before (c). A writer with a stale head gets `conflict`, whatever its batch holds.
- Steps 1–3 of (c) run for every entry, before step 4. A forged or malformed entry is refused
  even when the peer already holds its id.

A store never repairs. An entry whose id does not recompute is refused also when its arrival
record names the id the claims really have; the claims are never filed under the recomputed id.

Nothing else is ordered. When (a) and (b) both apply, the refusal of (a) and `conflict` both
conform; no vector reaches that case. When several entries of one batch are bad, the code is the
same.

A refusal commits nothing: no delta of the batch is held, and the head and revision do not move.
The revision advances exactly when the commit adds an id or changes the head. The largest
committed sequence never decreases, also not after a purge: a purged delta's sequence stays spent,
also when the purge leaves the peer holding nothing.

The store checks sequences for two things only: greater than the peer's largest, and distinct
among the batch's new entries. That sequences follow ascending id inside a transfer, and that one batch shares
one transfer ordinal, are admission's rules (SPEC-6 vNext §3). The store does not check them.

A store that cannot tell whether an append committed answers `uncertain`. The memory reference
store never does. In a conformance run `uncertain` fails the step.

**`purge(ids)`** answers a report (§1.5). For each distinct id, ascending:

| The peer… | Outcome | Effect |
|---|---|---|
| holds the id, and no other peer does | `removed` | The peer stops holding it. The store drops the bytes. |
| holds the id, and another peer does too | `held-by-other-peer` | The peer stops holding it. The bytes stay. The peer now **owes** the id. |
| does not hold it, but owes it, and the bytes are gone | `removed` | The debt ends. |
| does not hold it, but owes it, and the bytes remain | `held-by-other-peer` | Nothing changes. |
| neither holds nor owes it | `not-held` | Nothing changes. |

"Stops holding" removes the id from every answer of §1.4 for this peer, including its arrival
record. This holds for `held-by-other-peer` as for `removed`: the bytes stay, the holding ends.
When the peer appends the id again, it holds it under the new entry's appearance and arrival
record; nothing of the first holding comes back. The revision advances exactly when the peer stops holding at least one id. An append that
makes the peer hold an id again ends its debt for that id. A peer that never held an id always
gets `not-held`, whoever else holds it. A purge never changes another peer's answers or revision.
A store whose erasure class is `none` refuses every purge with `capability-absent`.

**What a purge reveals.** `held-by-other-peer` tells the peer that some other peer holds an id
this peer itself admitted. By asking again it learns when that holder lets go. It never learns
who. This is deliberate: a report may not say bytes are gone while they remain, so the peer must
learn that they remain. It learns nothing about an id it never held.

### 1.4 Snapshot

A snapshot has a `revision`, a `head`, and a `count` (how many deltas the peer holds). All three
are fixed when it is read.

| Operation | Answer |
|---|---|
| `get(ids)` | The held deltas among `ids`. Each carries the signature this peer admitted it with. |
| `arrivals(ids)` | This peer's arrival record for each held id among `ids`. |
| `targets(entities)` | Ids of held deltas with at least one pointer whose target is an entity reference to one of `entities`. Any role, any context. |
| `negators(ids)` | Ids of held deltas with at least one pointer whose role is exactly `negates` and whose target is a delta reference to one of `ids`. Direct negators only. The answer does not depend on whether the peer holds the negated id. |
| `scope(request)` | §1.4.1. |
| `release()` | Ends the snapshot. Every later operation refuses `snapshot-released`. |

Repeated ids or entities in a request change nothing. Unknown ids and entities yield nothing.

**Refusals on a snapshot** are `snapshot-released`, `snapshot-moved` and, after the store closes,
`store-closed`. When more than one applies, any of them conforms; their order is not pinned.

**The shape of a request comes first**, as in `append`. A `scope` with a bound outside its legal
values (§1.2) is refused `invalid-request` whatever the snapshot's state: on a moved snapshot and
on a released one too. This order is pinned by vector with three bounds on each of the two
snapshots: `1.5`, `-1` and 2^53 (9007199254740992). The first two stop at the boundary of a
witness whose bound is an unsigned integer, so for that witness they pin its runner (§3.7), not
its store. 2^53 fits an unsigned 64-bit field: it reaches the store in every witness, and it is
the bound that pins this order for a typed store.

**Repeatability.** When the peer's revision has passed the snapshot's, an operation MUST either
refuse `snapshot-moved` or answer exactly as it would have at the snapshot's revision. It MUST NOT
answer from the later state. The memory reference store refuses.

#### 1.4.1 Scope

`scope({anchors, pushdown?, exclude?})`. An anchor is `{"kind": "entity", "entity": <entity id>}`.
A store refuses `capability-absent` for an anchor kind it has no index for. Slice 1 has the one
kind, so no vector reaches this: a witness whose anchor type cannot hold another kind satisfies
the rule, and a dynamically typed witness refuses and tests it itself. `pushdown` has three
optional fields (their legal values are in the `invalid-request` list, §1.2):

| Field | A held delta passes when |
|---|---|
| `timestampAtMost: t` | its signed `timestamp` ≤ t |
| `arrivalAtMost: n` | its arrival `sequence` at this peer ≤ n |
| `excludeIds: [...]` | its id is not in the list |

Definitions. H is the peer's holdings. For a set of fields q, H_q is the members of H that pass
every field of q. For a set D of deltas, S(A over D) is SPEC-17 §4:

1. Start with every member of D that has a pointer to an entity among the anchors.
2. Add every member of D that negates (as in `negators`) a member already added. Repeat until
   nothing is added.

The answer is `{deltas, applied}`. `deltas` is a list of held deltas, R. `applied` has one boolean
per pushdown field. Let p be the requested fields, and q the fields reported applied.

- q ⊆ p. A store never reports a field that was not requested.
- **Lower bound:** `S(A over H_p) \ exclude ⊆ R`.
- **Upper bound:** `R ⊆ S(A over H_q)`.

`exclude` is not a selection. It lets the store leave ids out of R; negation chains still run
through excluded ids. `excludeIds` is a selection: a chain stops at a dropped id.

The selection applies **before** the walk. A store that walks the chains over H and filters the
result afterwards returns negations whose targets failed the selection, and breaks the upper
bound.

### 1.5 Purge report

`{claim, boundary, revision, targets, surfaces}`:

- `targets`: `{id, outcome}` for each distinct requested id, ascending.
- `revision`: the peer's revision after the purge.
- `boundary`: always the string `store-controlled-surfaces` (SPEC-18 §4.7.2, "the boundary of
  absent").
- `surfaces`: `{surface, state}` for each storage surface the store declares, in a fixed order.
  `state` is `absent`, `owed` or `unprovable`. The states speak for the targets this report marks
  `removed`. A target another peer still holds is told by its outcome, not by a surface.
- `claim`: what the store asserts about the bytes of the targets this report marks `removed`, and
  about no other target.
  - `nothing-removed`: no target has outcome `removed` (an empty purge, or only `not-held` and
    `held-by-other-peer`). The report asserts nothing about bytes.
  - `proven`: at least one target is `removed`, the store's class is `proven`, the store declares
    at least one surface, and every surface is `absent`.
  - `unproven`: at least one target is `removed` and the store does not claim proof. A store of
    class `unprovable` always says this. A store of class `proven` may say it at any time: a
    store may claim less than it could, never more.

Surface names and their number are the store's own. Only the memory reference store's are fixed:
`rows`, `index-entries` (targets, negators and arrival records), `process-memory`, in that order,
with states `absent`, `absent`, `unprovable`.

### 1.6 Profile

The runner reads four things:

- `capabilities.erasure`: `proven`, `unprovable` or `none`.
- `capabilities.journal`: boolean.
- `pushdown.{timestampAtMost, arrivalAtMost, excludeIds}`: booleans.
- `formatVersion`: a string.

A store whose `formatVersion` equals the file's `reference.formatVersion`
(`rhizomatic.store.memory/1`) is a **memory reference store**. It is held to the extra "reference"
rules below. Its profile in slice 1 is: `values`, `journal`, `views`, `derivedIndexes`, `digest`
false; `arrival` true; erasure `unprovable`; every pushdown field true; `writers: one-process`;
`atRest: trusted`; `changeRetention: none`; `indexedValueRoles` empty.

A memory reference store may be built with any subset of the three pushdown fields switched off.
It then ignores those fields and reports them not applied. **Each witness runs both files against
the reference store in all 8 subsets.** That is what exercises the residual path of the trim lemma.

## 2. Common header

Both files are one JSON object and start with the same keys.

```json
{
  "format": "rhizomatic-store-scripts/1",
  "note": "...",
  "reference": { "formatVersion": "rhizomatic.store.memory/1" },
  "peers": { "A": "ed25519:c3c3…", "B": "ed25519:a1a1…" },
  "deltas": [ { "name": "a-height", "id": "1e20…", "claims": { … } } ]
}
```

- `format` is `rhizomatic-store-scripts/1` or `rhizomatic-store-scope/1`. Refuse any other value.
- `peers` maps a peer name to a peer id. Steps use names. One name, `EMPTY`, maps to the empty
  string; it exists to be refused.
- `deltas` is the corpus. Steps use `name`. Fields:
  - `name`: unique in the file.
  - `id`: the content address.
  - `claims`: the JSON debug profile of [the main README](../README.md#delta--canonicalization-l0-delta).
  - `sig` (optional): a string. The delta is a signed appearance. Two entries (`short-sig`,
    `k-note-upper`) carry a malformed signature on purpose; pass the string through unchanged.
  - `forged` (optional, `true`): the `id` deliberately does not match the claims. Build the delta
    with exactly this id and these claims, without checking it. For every other entry a loader
    SHOULD check that the id recomputes.
- Two entries can share an `id` and differ in `sig`. They are two appearances of one id.

Wherever a step lists delta names for ids, the id is the named entry's `id`. Expected lists are
already in ascending id order; compare element by element.

## 3. `scripts.json`

```json
"scripts": [
  { "name": "purge", "spec": "SPEC-18 §4.7.2, §7", "requires": ["purge"], "steps": [ … ] }
]
```

Run each script on a **new, empty store**. Peer handles and snapshots live for one script.

`requires` lists what the store's profile must offer. An absent `requires` means none. A name
that is not in the table below is a defect of the document: the script fails with a message that
names it, whatever the store. Skip the script, and report it as skipped, when a requirement
fails:

| Requirement | Holds when |
|---|---|
| `purge` | `capabilities.erasure` is not `none` |
| `journal-absent` | `capabilities.journal` is false |

A step is an object with an `op`. A step passes when the store does what `expect` says.

**Refusals.** Where `expect` has an `error` key, the operation must refuse. `error` is one code,
or a list of codes:

```json
"expect": { "error": "peer-exists" }
"expect": { "error": ["posture-refused", "peer-exists"] }
```

With a list, more than one cause applies and their order is free: a refusal with any listed code
conforms. A refusal with a code that is not listed fails, and so does an answer.

### 3.1 `createPeer`

```json
{ "op": "createPeer", "peer": "A", "erasure": "unproven", "expect": { "status": "created" } }
{ "op": "createPeer", "peer": "P", "erasure": "proven",
  "expect": { "error": "posture-refused", "unlessStoreErasure": "proven" } }
```

- `{"status": "created"}`: the peer is created. Its handle reports posture `erasure` and the
  store's erasure class. Keep the handle under the name `peer`.
- `{"error": …}`: the store refuses (see "Refusals").
- With `unlessStoreErasure`: when the store's `capabilities.erasure` equals that value, the
  expectation is `{"status": "created"}` instead. No later step uses such a peer.

### 3.2 `openPeer`

```json
{ "op": "openPeer", "peer": "A", "expect": { "status": "opened", "posture": "unproven" } }
{ "op": "openPeer", "peer": "C", "expect": { "error": "peer-absent" } }
{ "op": "openPeer", "peer": "A", "handle": "A2", "expect": { "status": "opened", "posture": "unproven" } }
```

On `opened`, the handle reports that posture.

- Without `handle`, it replaces the handle kept under the name `peer`.
- With `handle`, keep the new handle under that name, and **keep the older handle** under the name
  it has. Both belong to the same peer and share one bookkeeping record (§3.3).

In `append`, `purge` and `read`, and in a scope case of `scope.json` (§4), the `peer` key is a
**handle name**. The bookkeeping is always that of the peer the handle belongs to. A peer's first handle has the
peer's own name, so most steps read the same either way. In `createPeer`, `openPeer` and `export`
the `peer` key is a name from `peers`.

### 3.3 `append`

```json
{ "op": "append", "peer": "A", "expectedHead": null, "nextHead": "head-1", "frame": null,
  "added": [ { "delta": "a-height",
               "arrival": { "at": 1001, "sequence": 1, "transfer": 1, "sender": "local" } } ],
  "expect": { "status": "committed", "added": ["a-height"], "revisionAdvanced": true } }
```

- `frame`: null, or hex bytes.
- `added[].delta`: a corpus name. The store receives that appearance.
- `added[].arrival`: the arrival record, passed to the store as written, also when a field is
  out of range (`sequence: 0`, `sequence: 1.5`, `sender: ""`, `transfer: 9007199254740992`). A
  witness whose record type cannot hold such a value answers for the store at its own boundary,
  **head first**: it reads the peer's current head; when the step's `expectedHead` differs, the
  step's answer is `conflict`; only otherwise is it the refusal `invalid-admission`. A stale
  writer gets `conflict` whatever its batch holds, in every witness. No vector combines a
  non-null `frame` with such a value, so that order stays free. Its `id` is the delta's id, unless the arrival object has
  an `id` key; then that key is a corpus name and the record carries that entry's id.
- `expect`, one of:
  - `{"status": "committed", "added": [names], "revisionAdvanced": bool}`. The result's ids equal
    the named ids. The result's revision equals the peer's revision after the step. That revision
    is greater than the revision before the step when `revisionAdvanced` is true, and equal when
    it is false.
  - `{"status": "conflict"}`. The revision does not change.
  - `{"error": …}`. The revision does not change.

Any other answer fails the step. That includes `uncertain`.

The runner reads the peer's revision by `read()` before and after the step.

**Bookkeeping.** For each peer the runner remembers which appearance and which arrival record each
held id was admitted with: on `committed`, for each id in the result, the first entry of `added`
with that id. A purge forgets every id in its report's `targets`, whatever the outcome: after
`removed` and after `held-by-other-peer` the peer holds the id no longer, and after the other
outcomes it held nothing to forget. So an id appended again is checked against its new arrival
record. Later steps check store answers against this record.

### 3.4 `purge`

```json
{ "op": "purge", "peer": "A", "ids": ["a-height-neg", "a-height", "far"],
  "expect": {
    "targets": [ { "delta": "a-height-neg", "outcome": "removed" },
                 { "delta": "a-height", "outcome": "held-by-other-peer" },
                 { "delta": "far", "outcome": "not-held" } ],
    "revisionAdvanced": true,
    "claim": { "unprovable": "unproven", "proven": "proven" },
    "referenceSurfaces": [ { "surface": "rows", "state": "absent" },
                           { "surface": "index-entries", "state": "absent" },
                           { "surface": "process-memory", "state": "unprovable" } ] } }
```

`expect.claim` is one of two objects: `{"unprovable": "unproven", "proven": "proven"}` when a
target is `removed`, and `{"unprovable": "nothing-removed", "proven": "nothing-removed"}` when
none is. A `claim` with any key other than `unprovable` and `proven`, or without one of them, is
a defect of the document: the step fails, whatever the store answers.

A `claim` has no entry for class `none`. A store of class `none` refuses every purge (§1.3), and
every script that purges requires `purge`, so the runner skips it for such a store. If a store
of class `none` reaches a purge step anyway, the step fails: there is no expectation for it. The
refusal itself is a test of each witness (§6, test 8), not a rule of the runner.

Checks:

- The purge answers. A refusal fails the step.
- The report's `targets` equal `expect.targets`, in order, by id and outcome.
- The report's `revision` is the peer's revision after the step; `revisionAdvanced` as in §3.3.
- `boundary` is `store-controlled-surfaces`.
- Let E be `expect.claim[<the store's erasure class>]`. The report's `claim` must equal E, with
  one exception: where E is `proven`, `unproven` also conforms. Nothing else is exchanged: `proven`
  never conforms where E is `unproven` or `nothing-removed`, and `unproven` never conforms where E
  is `nothing-removed`.
- Every surface state is one of the three values.
- If `claim` is `proven`: the surface list is not empty and every state is `absent`.
- **Reference:** a memory reference store's `surfaces` equal `referenceSurfaces` exactly, in order.

### 3.5 `read` and `release`

```json
{ "op": "read", "peer": "A", "snapshot": "s1" }
{ "op": "release", "snapshot": "s1" }
```

`read` takes a snapshot of the peer and keeps it under the name `snapshot`, with the peer it
belongs to. `release` releases it. Neither has an `expect`.

### 3.6 Snapshot fields: `head`, `count`

```json
{ "op": "head", "snapshot": "s", "expect": { "head": "head-1" } }
{ "op": "count", "snapshot": "s", "expect": { "count": 7 } }
```

These read the values fixed when the snapshot was read. They never refuse, also not on a moved or
released snapshot.

### 3.7 Queries: `get`, `arrivals`, `targets`, `negators`, `scope`

```json
{ "op": "get",      "snapshot": "s", "ids": ["a-name", "ghost"], "expect": { "deltas": ["a-name"] } }
{ "op": "arrivals", "snapshot": "s", "ids": ["a-name", "ghost"], "expect": { "ids": ["a-name"] } }
{ "op": "targets",  "snapshot": "s", "entities": ["plant:a"],    "expect": { "ids": ["a-name", "a-height"] } }
{ "op": "negators", "snapshot": "s", "ids": ["a-height"],        "expect": { "ids": ["a-height-neg"] } }
{ "op": "scope",    "snapshot": "s",
  "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
  "pushdown": { "timestampAtMost": 30, "arrivalAtMost": 4, "excludeIds": ["a-name"] },
  "exclude": ["a-height"],
  "expect": { "lower": ["a-height-neg"], "upper": ["a-name", "a-height-neg", "a-height"] } }
```

Ask the store first and judge the answer afterwards: a store that answers where the step expects
a refusal fails for that, whatever it answered.

`expect` is one of three shapes:

1. A result, as below. The operation must answer, and the answer must match.
2. A result with `"orError": "snapshot-moved"`. The operation either refuses `snapshot-moved`, or
   answers and the answer matches. Any other answer or refusal fails.
3. `{"error": …}`. The operation must refuse (see "Refusals"). A snapshot that is both released
   and moved carries `["snapshot-released", "snapshot-moved"]`.

Result checks:

- `get`: the returned ids equal the named ids. Each returned delta is the **named appearance**:
  same id, same `sig` (absent when the entry has none), and claims that recompute to the id.
- `arrivals`: the returned records' ids equal the named ids. Each record equals the one the
  runner's bookkeeping holds for this peer and id, field by field.
- `targets`, `negators`: the returned ids equal the named ids.
- `scope`: `pushdown` and `exclude` are optional; their id lists are corpus names. A bound is
  passed as written, also when it is out of range (`arrivalAtMost: 1.5`, `-1`,
  `9007199254740992`); a witness whose type cannot hold the value refuses `invalid-request` at its
  own boundary. A witness whose type can hold the value MUST pass it to the store: its runner
  does not answer for the store. Then:
  - R is ascending by id with no id twice.
  - Every member of R is held by the snapshot's peer per the bookkeeping, has claims that
    recompute to its id, carries the signature of the appearance that peer admitted, and carries
    that peer's arrival record.
  - `applied` reports no field that was not requested.
  - Every id of `lower` is in R. Every id of R is in `upper`. Here `lower` is
    `S(A over H_p) \ exclude` and `upper` is `S(A over H)`. This `upper` is the loose bound; the
    exact upper bound of §1.4.1 is checked in `scope.json`.
  - **Reference:** a memory reference store reports `applied[f]` true exactly for each requested
    field whose profile entry is true. When it applied every requested field, R equals `lower`.

### 3.8 Export

```json
{ "op": "export", "peer": "A", "expect": { "deltas": ["b-name", "a-height"] } }
{ "op": "export", "peer": "C", "expect": { "error": "peer-absent" } }
{ "op": "exportStored", "expect": { "ids": ["b-name", "a-height", "far"] } }
{ "op": "exportPeers", "expect": { "peers": ["B", "A"] } }
```

- `export`: `admin.peer(peer).ids()` equals the named ids. `admin.peer(peer).deltas()` yields the
  same count, and each is the named appearance (as `get`). A refusal may come when the listing is
  read.
- `exportStored`: `admin.storedIds()` equals the named ids. An id two peers hold appears once.
- `exportPeers`: `admin.peers()` equals the ids of the named peers, in the listed order.

## 4. `scope.json`

```json
{
  "format": "rhizomatic-store-scope/1", "note": "…", "reference": { … }, "peers": { … },
  "deltas": [ … ],
  "setup": [ <steps> ],
  "cases": [
    { "name": "signed-time-cuts-a-chain", "spec": "SPEC-18 §4.3", "peer": "A",
      "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
      "selection": { "timestampAtMost": 30 },
      "held": [],
      "scopes": [ { "fields": [], "ids": [ … ] },
                  { "fields": ["timestampAtMost"], "ids": [ … ] } ] }
  ]
}
```

Open **one** new store. Run `setup`: steps in the §3 format, with the same checks and bookkeeping.
Then run every case against that store. Cases only read.

A case:

- `selection`: the read's whole selection, in pushdown form (§1.4.1). Its present fields are P.
- `peer`: a handle name (§3.2). The setup opens a second handle of one peer, and one case reads
  through it.
- `held`: ids the read already holds. The peer holds all of them. They stand for what earlier
  rounds of the **same read on the same snapshot** fetched. The lemma does not hold for deltas
  held from another snapshot.
- `scopes`: one entry for **every subset** f of P (2^|P| entries). `fields` lists f in the fixed
  order `timestampAtMost`, `arrivalAtMost`, `excludeIds`. `ids` is `S(A over H_f)`: the scope when
  only the fields of f select.
- The entry with `fields` = P is the **exact scope** of the read.

For each entry f of `scopes`, on one snapshot of `peer`:

1. Call `scope` with the anchors, `exclude` = `held`, and `pushdown` = the fields of `selection`
   that are in f. Omit `pushdown` when f is empty.
2. Check R as in §3.7: ascending, held, right appearance, right arrival record.
3. Let q be the fields reported applied. q ⊆ f, else fail.
4. **Lower bound:** every id of `scopes[f].ids` that is not in `held` is in R.
5. **Upper bound:** every id of R is in `scopes[q].ids`.
6. **Reference:** a memory reference store reports q = f restricted to the fields its profile
   offers, and R equals `scopes[q].ids` minus `held` exactly.
7. **Trim lemma.** The host's residual selection is the fields of P not in q. Build the set
   D′ = (members of R that pass the residual fields) ∪ (the held deltas of `held`, with the
   arrival records from the bookkeeping, that pass every field of P). The held deltas are the
   appearances the peer admitted: a runner takes them from its bookkeeping, or reads them with
   `get` on the same snapshot. Compute S(A over D′) in the runner. It MUST equal the exact scope.

Step 7 is the lemma: whatever the store applied, the host reaches the same scope from R and what
it already holds. A store that reports an applied field but returns members that fail it breaks
step 5. A store that drops a member the selection keeps breaks step 4.

## 5. What the vectors do not cover

- The change feed, the journal, stored views, derived indexes, value-lookup and derived-index
  anchors, digests. Slice 1 has none of them.
- An unknown anchor kind, a missing posture, and non-finite numbers (§1.2, §1.4.1). JSON or a
  typed witness cannot express them; each witness tests what its language can express.
- **Ownership** (§1, "A store owns what it holds", "A store never converts"). A conformance run
  hands a store values and compares what comes back; it never changes a value afterwards and
  never passes a value of the wrong type. A store that keeps the caller's objects, returns its
  own, or shares a payload's memory passes every vector. Ownership is an obligation of each
  witness and of each store, with its own tests (§6).
- A purge on a store of class `none`. The scripts that purge are skipped for such a store, so no
  shared step shows that it refuses. Each witness tests that refusal for its own stores (§6,
  test 8).
- Proof of physical absence. The memory reference store is `unprovable`. A `proven` store adds
  its own adapter rails for its surfaces (SPEC-18 §8).
- Cost. A JSON file cannot measure work. Each witness has its own cost rails (SPEC-18 §8):
  - **Core operations.** A rail asserts that no core operation walks a whole set. A memory store
    may count its own index work for this, as the reference does.
  - **Building `scopeSource`.** A rail times the build from outside, with a monotonic clock. It
    builds the source from N members at one entity and from 8N, and takes the fastest of three
    builds of each. The ratio must stay below 24: linear work gives about 8, and quadratic work
    about 64. It repeats this for N and 8N negations of one delta. N is large enough that the
    build at N takes about 50 ms or more. This is a coarse scaling check, not a count: it catches
    a copy or a search of a bucket per insert, and it cannot see a quadratic term too small to
    show at that N. A count kept by the code under test does not serve, because that code can
    do work it does not count.
- `store-closed`, `openStore` and URL schemes. These are host API, tested per witness. One rule
  binds every witness that opens by URL: the options of `openStore` are absent (none) or a plain
  object, and its `requires` is absent (none) or a list of strings. A dynamically typed witness
  refuses anything else with `invalid-request` and one fixed message that quotes nothing the
  caller gave, reads the options once, and hands the store's factory its own copy.
- The runner. The vectors judge a store through a runner, and nothing in the vectors judges the
  runner (§7).

## 6. What a store tests for itself: ownership

A store that passes the vectors has not shown that it owns what it holds. Whoever writes a store,
a witness or a consumer, tests these for that store. Each test changes a value the test still
holds and then reads the store again; the store's answers MUST NOT change.

1. **After append.** Append a signed delta with a bytes payload, to two peers. Then change every
   part of what was appended: each claims field, a pointer's role and target, the list of
   pointers, the payload's bytes, the signature, the id, each field of the arrival record. Every
   read of both peers answers as before.
2. **After a read.** Change every part of what `get`, `arrivals`, `scope` and the exporter
   returned, the payload's bytes and the memory behind them included. Every later read, of this
   peer and of every other peer that holds the id, answers as before. Two reads of one id share
   no memory with each other.
3. **Payload memory.** For every byte container the language has, append a payload held in it,
   then write to the caller's memory. The store's bytes do not change. In TypeScript the
   containers are a plain `Uint8Array`, a Node `Buffer`, a subclass, a view of part of a larger
   buffer, and a view over shared memory; in Rust the type system gives this for owned vectors,
   and a store that takes shared or borrowed bytes tests it.
4. **No conversion** (a dynamically typed witness). For each position of an entry, pass a value
   of another type that a lenient store could convert: a buffer or a list of numbers for a
   payload, a numeric string for a number, a string object for a string, an object with indexes
   for a list. Use the id the converted form would have. The store refuses and holds nothing.
5. **One read of each field** (a witness whose objects can answer differently on each read). For
   every field the store keeps or acts on, pass a value that is honest on its first read and
   wrong on every later read. The fields are: each field of the claims; the signature; the
   delta's id; each of the five fields of the arrival record; and the fields of a request (the
   ids of `get`, `arrivals`, `negators` and `purge`, the entities of `targets`, and the anchors,
   the bounds, `excludeIds` and `exclude` of `scope`). The store may admit or refuse. If it
   admits, what it keeps and answers is a value it checked: it MUST NOT hold the id over claims
   that do not recompute, keep a signature or an arrival record that its checks would refuse,
   or answer a request other than the one it checked. A store that reads each field once admits
   every such entry and keeps the honest values.
6. **The profile.** Change the profile a caller reads, or replace it. The posture gate and the
   applied pushdown fields do not change. Nothing the store decides by is reachable from a
   handle.
7. **`scopeSource`.** It has one input, the list of members, and its answers. Build a source
   from a list of members, then repeat tests 1 to 5 against it: change the members and the list
   after the build, change what `get` and `arrival` return, and pass members whose fields answer
   differently on each read. Its answers (`get`, `arrival`, `targets`, `negators`, `ids`) MUST
   NOT change, and it MUST NOT file a member under an id its claims do not recompute to. Test 3
   applies to the payload of a member. Tests that need two peers do not apply.
8. **A store of class `none`.** Every `purge` refuses `capability-absent`, an empty purge too,
   and changes nothing: the holdings, the head and the revision stay. A witness that has no store
   of class `none` has nothing to test here.

## 7. What a witness tests for itself: the runner

A runner that stops checking a rule still passes the memory store, so the vectors cannot hold a
runner to this page. Each witness keeps a table of wrong stores, one per rule of §3 and §4. A
wrong store is the memory store behind a thin wrapper that breaks that one rule and nothing a
script meets before it. For each, the conformance run MUST fail, in the expected document, with
the message of that rule. Asserting the message matters: a script stops at its first failing
step, and many wrong answers are caught by a later, unrelated check when the rule's own check is
gone.

The table covers at least:

- **Refusals:** a code outside the step's list, for `createPeer`, `openPeer`, `append`, a query
  and `export`; an answer where a refusal is expected; a refusal where an answer is expected; on
  a moved snapshot, a refusal that is not `snapshot-moved`.
- **Peers:** a created or opened handle with another posture; a created handle with another
  erasure class than the profile; `unlessStoreErasure` in both directions.
- **Append:** each answer that is not the expected one, `uncertain` included; the added ids, and
  their order; the result's revision; a refused append or a `conflict` that moves the revision,
  up and down; `revisionAdvanced` in both directions.
- **Purge:** outcomes (not ids only), their order, a repeated id; the report's revision;
  `revisionAdvanced` in both directions; the boundary text, exactly; each claim that is not the
  expected one; `proven` with no surface and with a surface that is not `absent`; a surface state
  outside the three.
- **The bookkeeping:** the first entry of a batch with an id is the one held; a purge forgets
  the id, so an id appended again is held under its new arrival record. Both outcomes that end
  a holding: a store that keeps the old record after `removed`, and one that keeps it after
  `held-by-other-peer`.
- **Point reads:** `head`, and a new peer's head that is the empty string instead of null;
  `count`; ids and their order for `get`, `arrivals`, `targets`, `negators`; a returned delta's
  signature and claims; each of the four fields of an arrival record.
- **Scope members:** order, a repeat, claims, the arrival record's id and fields, the signature,
  a member the peer does not hold.
- **Scope bounds:** `applied` ⊆ requested; the lower and the upper bound in a script and in a
  scope case; the trim comparison. In a scope case, the lower bound twice: a store that leaves
  out the first id of the bound, and one that leaves out a later id.
- **Reference rules:** the applied fields, the exact ids in a script and in a scope case, the
  surfaces. For each, the same wrong answer under another `formatVersion` conforms. The exact
  ids in a script also for a step with no `pushdown`: a store that ignores `exclude` only when
  no pushdown is asked.
- **Export:** ids, their order, the count of deltas in both directions (fewer deltas than ids,
  and more), a delta's appearance; the stored listing and the peer listing.
- **Requirements:** each one skips exactly its scripts and reports them; each script gets a new
  store.
- **Documents:** an unknown `format`; a corpus id that does not recompute and is not `forged`; a
  purge `claim` with a key other than `unprovable` and `proven`; an unknown script requirement.

A rule a wrapped store cannot reach is listed by name in the test file, with the reason. Then the
table itself is checked once: for each check of the runner, remove it and see the table go red.

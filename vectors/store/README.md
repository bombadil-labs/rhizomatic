# Store vectors

These files pin the store interface of [SPEC-18](../../spec/18-store.PROPOSAL.md) (proposal),
slice 1: peers and postures, append, point reads, the scope query, purge, snapshots and export;
from slice 2, the read in rounds over a store; and, from slice 3, the change feed (§3.9),
freshness (§9) and following the feed (§10). This page is the format contract. An
implementer needs this page, SPEC-18 §4, SPEC-17 §5 and §6 for the reads, and the JSON files, and
no witness source.

| File | Contents |
|---|---|
| `scripts.json` | Operation scripts. Each step names its expected ids, report or refusal. |
| `scope.json` | The trim lemma (SPEC-18 §4.3): one holding set, then scope cases. |
| `rounds.json` | A read in rounds (SPEC-18 §4.4): one holding set, then reads. It tests a **reader**, not a store. §5. |
| `freshness.json` | Captures, `touching` and `checkFresh` (SPEC-18 §4.6) over the change feed. It tests a store and a witness's freshness functions. §9. |
| `follow.json` | The feed cursor (SPEC-18 §4.6, "Following the feed"). It tests a store and a witness's follower. §10. |

`scripts.json` and `scope.json` are generated by `implementations/ts/tools/gen-store-vectors.ts`,
`rounds.json` by `implementations/ts/tools/gen-store-round-vectors.ts`, `freshness.json` by
`implementations/ts/tools/gen-store-freshness-vectors.ts`, and `follow.json` by
`implementations/ts/tools/gen-store-follow-vectors.ts` (all run in `npm run gen-vectors`). Expectations come from a model that scans plain lists, not from a store.
The memory store must pass the store documents before the generator writes them. CI regenerates
the files and compares bytes.

A **store** conformance run covers `scripts.json` and `scope.json`, both. `scripts.json` alone
does not hold a store to the exact upper bound of a scope (§1.4.1); only `scope.json` does. A
runner's default is both. `rounds.json` is run by each witness's own tests against its
store-backed read (§5).

## 1. What a witness must provide

A witness runs the vectors against a **store**. The operations below are SPEC-18 §4 in neutral
form. Names are the vectors' names; a witness spells them in its own idiom. A Rust store is
synchronous; "refuses with `code`" means it returns an error value that carries that code.

**A store owns what it holds; no caller holds a reference into it.** A store keeps its own copy
of every delta, signature and arrival record it is given. Changing a value after it was appended
changes nothing in the store. Changing a value a store returned changes nothing in the store, for
this peer or any other. This holds for every part of a delta, a bytes payload included: a copy
must not share memory with what the caller holds. It holds for the store's profile too: the
profile a caller reads is not the object the store decides by, and no caller can reach that
object. A store keeps only the canonical fields of a delta's claims (SPEC-1 §2); anything else a
caller attached is not stored and not served.

**A store never converts what it is given.** It takes a value only when the value has the type
its position requires, and refuses every other value. A bytes payload must be the witness's byte
array type; a buffer the payload could be built from, a number, a list of numbers and an array of
another element size are refused, not turned into bytes. The claims a store hashes are the claims
it keeps: it checks and hashes its own copy, so nothing the caller does between the check and the
copy can put other claims under an id. The refusal is `invalid-admission` in `append` and
`invalid-request` everywhere else. A witness whose types cannot hold a wrong value satisfies the
rule by its types. No vector reaches this rule (§6).

**Handles are owned.** A peer handle and a snapshot stay usable for as long as the store is open.
Opening a peer again does not end an older handle of that peer: both are views of one peer, and
each sees what the other wrote. So `snapshot-moved` and `snapshot-released` are refusals at run
time in every witness, never something a type system rules out.

### 1.1 Values

- **Id**: a delta's content address, lowercase hex.
- **Delta**: `{id, claims, sig?}`. Two deltas with one id and different `sig` are two
  **appearances** of one id.
- **Arrival record** (SPEC-6 vNext §3): `{id, at, sequence, transfer, sender}`.
  - `sequence` and `transfer` are integers from 1 to 2^53 − 1 (9007199254740991), in every
    witness. JSON carries both bounds exactly.
  - `at` is a finite number of milliseconds. It may be fractional: SPEC-6 vNext §3 takes it from
    the receiver's clock and does not restrict it to integers.
  - `sender` is a non-empty string.
- **Signature**: when present, exactly 128 lowercase hexadecimal characters (SPEC-1 §5, the form
  the `l0-delta` signed vectors use). The store checks the form, never the signature itself.
- **Held delta**: a delta with the arrival record of the peer that holds it.
- **Head**: an opaque non-empty string, or null when the peer never committed an append. Two
  heads are equal when they are the same string, byte for byte. No case folding, no trimming.
  Null is not the empty string: an `expectedHead` of `""` never matches.
- **Revision**: an integer from 0 to 2^53 − 1, ordered inside one peer. The slice 1 and 2 vectors
  use only "equal" and "greater". The feed vectors also add a small integer to a named revision
  to name one past the current revision (§3.9).
- **Order.** Every list of ids, deltas or arrival records a store returns is ascending by the
  UTF-8 bytes of the id, with no id twice. Peer ids are listed ascending the same way.

### 1.2 Store

| Operation | Result |
|---|---|
| `profile` | The store's declared profile (§1.6). |
| `createPeer(peerId, erasure)` | A peer handle. `erasure` is the posture: `proven` or `unproven`. |
| `peer(peerId)` | A handle to an existing peer. |
| `admin.peers()` | Every peer id. |
| `admin.peer(peerId).ids()` | The ids that peer holds. |
| `admin.peer(peerId).deltas()` | The same members, each as that peer admitted it. |
| `admin.storedIds()` | Every id the store keeps bytes for, once each, whichever peers hold it. |

A peer handle exposes its posture and the store's erasure class recorded at creation. A new peer
holds nothing: its head is null and its count is 0. Its revision is whatever the store starts at;
the first commit is greater.

Refusals:

| Code | When |
|---|---|
| `posture-refused` | `createPeer` with posture `proven` on a store whose erasure class is not `proven`. Nothing is created. |
| `peer-exists` | `createPeer` for an id that exists. |
| `peer-absent` | `peer`, or an `admin.peer(...)` listing, for an id that does not exist. `peer` never creates. |
| `invalid-request` | `createPeer` with an empty peer id, or with no posture or a value that is not a posture. |

When `createPeer` has two causes at once (posture `proven` on a store that is not `proven`, for an
id that exists), `posture-refused` and `peer-exists` both conform.

**`invalid-request`, the closed list for slice 1:**

1. `createPeer` with an empty peer id, or without one of the two postures.
2. `scope` with a `timestampAtMost` that is not a finite number.
3. `scope` with an `arrivalAtMost` that is not an integer from 0 to 2^53 − 1. (0 is legal and
   selects nothing, because sequences start at 1.)
4. A requirement name at open that is not in the store's list of requirement names.
5. The synchronous source over a fetched scope (`scopeSource`), given a member whose id does not
   recompute from its claims, or a member with a value that is not of its type. The first
   appearance of an id is kept and checked; a repeated id is not examined. A refused call adds
   nothing: the source is unchanged, or is not built. The source owns its members as a store
   does: it copies them in without converting, and what it returns cannot be used to change it.
   Building the source costs the total size of its members: N members at one entity, N
   negations of one delta, one member with N entity pointers, and N appearances of a few ids
   cost N steps and not N². Each witness has a rail for this (§6, "Cost").
6. In a dynamically typed witness only: a request with a value that is not of its type. A list of
   ids or entities that is not a list of strings, an anchor that is not an object with a kind, a
   `createPeer` whose options are absent or not a plain object (item 7), or whose `erasure`
   throws when read. A typed witness cannot receive one.
7. In a dynamically typed witness only: an optional object field that is present and is not a
   plain object. "Absent" means the field is not given (in TypeScript, `undefined`); then it means
   none. Any other value is refused, also `null`, a list, a number, a string, a boolean and a
   function: a store never reads such a value as an empty object. Slice 1 has two such fields:
   the `pushdown` of `scope`, and the options of opening a store (§6, "`openStore`"). A plain
   object is one whose prototype is null or is some realm's `Object.prototype`, judged by the
   shape of the chain and not by identity with this realm's: an object literal from another
   realm is plain, as a list from another realm is a list. A class instance, and an object
   whose prototype is another object, are not plain.

A witness whose types make a case unrepresentable (a missing posture, a NaN in an integer field)
satisfies it. Vectors cover the empty peer id and the three `arrivalAtMost` refusals. JSON cannot
carry NaN or an infinity, so a non-finite `timestampAtMost` or `at` is a unit test in each witness.

### 1.3 Peer

**`history`** is an opaque, non-empty string: the identity of this peer's revision history in
this store (SPEC-18 §4.6). Compare two values for equality only. It stays the same while the
peer's revisions only advance. A peer created anew, also under a name that existed before, and a
store restored to an earlier state, carry another value. A value that starts with
`memory:local:` is unique only within one process (the TypeScript memory store's default); a
capture that carries one does not cross a process (SPEC-18 §4.6). The runner checks, by equality only
(a value cannot be pinned):

- After `createPeer`, the handle's `history` is a non-empty string, else
  `the peer's history is not a non-empty string`; and no other peer of the store has it, else
  `two peers of one store share the history <h>`.
- After `openPeer`, the handle reports the peer's value, else
  `a handle of <peer> reports another history than the peer's`.
- Every snapshot the runner reads (each `read` step, and each `read()` it makes to learn a
  revision) reports the peer's value, else
  `a snapshot of <peer> reports another history than the peer's`.

No script deletes a peer or restores a store. Each witness tests itself that one name created in
two stores has two values. Both witnesses carry `history` and make these checks.

A store never issues one history twice. The memory store's `mintHistory(peer)` takes the peer's
id and runs after every other check of `createPeer`, `peer-exists` included. A minted history
that is empty, starts with `memory:local:`, or repeats one this store issued to any peer, now or
before, is refused `invalid-request`, and no peer is created (SPEC-18 §4.6, §4.13 reading 49). A
script cannot pass a mint, so each witness tests this itself.

**`read()`** returns a snapshot at the peer's current revision.

**`append({expectedHead, nextHead, frame, added})`**, where `added` is a list of held deltas.
The checks:

- **(a) Shape of the call.** `nextHead` is empty: refuse `invalid-admission`. `frame` is not null
  and the profile's `journal` capability is false: refuse `capability-absent`. In a dynamically
  typed witness, a call that is not an object, or a `nextHead` that is not a string, is refused
  `invalid-admission` here; an `added` that is not a list is refused in (c), after the head.
- **(b) The head.** The peer's head is not equal to `expectedHead`: answer `conflict`. Nothing
  changes.
- **(c) The batch.** Walk `added` in order. For each entry:
  1. The entry, its delta, its claims, its signature or its arrival record holds a value that is
     not of its type (a dynamically typed witness only); or the id does not recompute from the
     claims (SPEC-1 §4): refuse `invalid-admission`.
  2. A signature is present and is not 128 lowercase hex characters: refuse `invalid-admission`.
  3. The arrival record's `id` is not the delta's id; or `sequence` or `transfer` is not an
     integer from 1 to 2^53 − 1; or `at` is not a finite number; or `sender` is empty: refuse
     `invalid-admission`.
  4. The peer already holds the id, or an earlier entry of this batch has it: skip the entry.
     The peer keeps the appearance and the arrival record it already has; this entry's signature
     and arrival record are ignored.
  5. `sequence` is not greater than the largest sequence this peer ever committed, or equals the
     sequence of an earlier **new** entry of this batch: refuse `invalid-admission`. A skipped
     entry (step 4) spends no sequence: its sequence is not compared with anything, a later new
     entry may carry the same number, and it does not raise the peer's largest committed sequence.
     This holds for both kinds of skipped entry, and a vector pins each: an entry whose id the
     peer held before the batch, and a repeat of an id inside the batch.
  6. Otherwise the entry is **new**.
- **(d) Commit**, all together: the peer holds every new delta with its arrival record and
  signature; the head becomes `nextHead`. Answer `committed` with the new ids (ascending) and the
  revision.

**Order.** Two orders are pinned by vector:

- (b) comes before (c). A writer with a stale head gets `conflict`, whatever its batch holds.
- Steps 1–3 of (c) run for every entry, before step 4. A forged or malformed entry is refused
  even when the peer already holds its id.

A store never repairs. An entry whose id does not recompute is refused also when its arrival
record names the id the claims really have; the claims are never filed under the recomputed id.

Nothing else is ordered. When (a) and (b) both apply, the refusal of (a) and `conflict` both
conform; no vector reaches that case. When several entries of one batch are bad, the code is the
same.

A refusal commits nothing: no delta of the batch is held, and the head and revision do not move.
The revision advances exactly when the commit adds an id or changes the head. The largest
committed sequence never decreases, also not after a purge: a purged delta's sequence stays spent,
also when the purge leaves the peer holding nothing.

The store checks sequences for two things only: greater than the peer's largest, and distinct
among the batch's new entries. That sequences follow ascending id inside a transfer, and that one batch shares
one transfer ordinal, are admission's rules (SPEC-6 vNext §3). The store does not check them.

A store that cannot tell whether an append committed answers `uncertain`. The memory reference
store never does. In a conformance run `uncertain` fails the step.

**`purge(ids)`** answers a report (§1.5). For each distinct id, ascending:

| The peer… | Outcome | Effect |
|---|---|---|
| holds the id, and no other peer does | `removed` | The peer stops holding it. The store drops the bytes. |
| holds the id, and another peer does too | `held-by-other-peer` | The peer stops holding it. The bytes stay. The peer now **owes** the id. |
| does not hold it, but owes it, and the bytes are gone | `removed` | The debt ends. |
| does not hold it, but owes it, and the bytes remain | `held-by-other-peer` | Nothing changes. |
| neither holds nor owes it | `not-held` | Nothing changes. |

"Stops holding" removes the id from every answer of §1.4 for this peer, including its arrival
record. This holds for `held-by-other-peer` as for `removed`: the bytes stay, the holding ends.
When the peer appends the id again, it holds it under the new entry's appearance and arrival
record; nothing of the first holding comes back. The revision advances exactly when the peer stops holding at least one id. An append that
makes the peer hold an id again ends its debt for that id. A peer that never held an id always
gets `not-held`, whoever else holds it. A purge never changes another peer's answers or revision.
A store whose erasure class is `none` refuses every purge with `capability-absent`.

**What a purge reveals.** `held-by-other-peer` tells the peer that some other peer holds an id
this peer itself admitted. By asking again it learns when that holder lets go. It never learns
who. This is deliberate: a report may not say bytes are gone while they remain, so the peer must
learn that they remain. It learns nothing about an id it never held.

### 1.4 Snapshot

A snapshot has a `revision`, the peer's `history`, a `head`, and a `count` (how many deltas the
peer holds). All four are fixed when it is read.

| Operation | Answer |
|---|---|
| `get(ids)` | The held deltas among `ids`. Each carries the signature this peer admitted it with. |
| `arrivals(ids)` | This peer's arrival record for each held id among `ids`. |
| `targets(entities)` | Ids of held deltas with at least one pointer whose target is an entity reference to one of `entities`. Any role, any context. |
| `negators(ids)` | Ids of held deltas with at least one pointer whose role is exactly `negates` and whose target is a delta reference to one of `ids`. Direct negators only. The answer does not depend on whether the peer holds the negated id. |
| `scope(request)` | §1.4.1. |
| `release()` | Ends the snapshot. Every later operation refuses `snapshot-released`. |

Repeated ids or entities in a request change nothing. Unknown ids and entities yield nothing.

**Refusals on a snapshot** are `snapshot-released`, `snapshot-moved` and, after the store closes,
`store-closed`. When more than one applies, any of them conforms; their order is not pinned.

**The shape of a request comes first**, as in `append`. A `scope` with a bound outside its legal
values (§1.2) is refused `invalid-request` whatever the snapshot's state: on a moved snapshot and
on a released one too. This order is pinned by vector with three bounds on each of the two
snapshots: `1.5`, `-1` and 2^53 (9007199254740992). The first two stop at the boundary of a
witness whose bound is an unsigned integer, so for that witness they pin its runner (§3.7), not
its store. 2^53 fits an unsigned 64-bit field: it reaches the store in every witness, and it is
the bound that pins this order for a typed store.

**Repeatability.** When the peer's revision has passed the snapshot's, an operation MUST either
refuse `snapshot-moved` or answer exactly as it would have at the snapshot's revision. It MUST NOT
answer from the later state. The memory reference store refuses.

#### 1.4.1 Scope

`scope({anchors, pushdown?, exclude?})`. An anchor is `{"kind": "entity", "entity": <entity id>}`.
A store refuses `capability-absent` for an anchor kind it has no index for. Slice 1 has the one
kind, so no vector reaches this: a witness whose anchor type cannot hold another kind satisfies
the rule, and a dynamically typed witness refuses and tests it itself. `pushdown` has three
optional fields (their legal values are in the `invalid-request` list, §1.2):

| Field | A held delta passes when |
|---|---|
| `timestampAtMost: t` | its signed `timestamp` ≤ t |
| `arrivalAtMost: n` | its arrival `sequence` at this peer ≤ n |
| `excludeIds: [...]` | its id is not in the list |

Definitions. H is the peer's holdings. For a set of fields q, H_q is the members of H that pass
every field of q. For a set D of deltas, S(A over D) is SPEC-17 §4:

1. Start with every member of D that has a pointer to an entity among the anchors.
2. Add every member of D that negates (as in `negators`) a member already added. Repeat until
   nothing is added.

The answer is `{deltas, applied}`. `deltas` is a list of held deltas, R. `applied` has one boolean
per pushdown field. Let p be the requested fields, and q the fields reported applied.

- q ⊆ p. A store never reports a field that was not requested.
- **Lower bound:** `S(A over H_p) \ exclude ⊆ R`.
- **Upper bound:** `R ⊆ S(A over H_q)`.

`exclude` is not a selection. It lets the store leave ids out of R; negation chains still run
through excluded ids. `excludeIds` is a selection: a chain stops at a dropped id.

The selection applies **before** the walk. A store that walks the chains over H and filters the
result afterwards returns negations whose targets failed the selection, and breaks the upper
bound.

### 1.5 Purge report

`{claim, boundary, revision, targets, surfaces}`:

- `targets`: `{id, outcome}` for each distinct requested id, ascending.
- `revision`: the peer's revision after the purge.
- `boundary`: always the string `store-controlled-surfaces` (SPEC-18 §4.7.2, "the boundary of
  absent").
- `surfaces`: `{surface, state}` for each storage surface the store declares, in a fixed order.
  `state` is `absent`, `owed` or `unprovable`. The states speak for the targets this report marks
  `removed`. A target another peer still holds is told by its outcome, not by a surface.
- `claim`: what the store asserts about the bytes of the targets this report marks `removed`, and
  about no other target.
  - `nothing-removed`: no target has outcome `removed` (an empty purge, or only `not-held` and
    `held-by-other-peer`). The report asserts nothing about bytes.
  - `proven`: at least one target is `removed`, the store's class is `proven`, the store declares
    at least one surface, and every surface is `absent`.
  - `unproven`: at least one target is `removed` and the store does not claim proof. A store of
    class `unprovable` always says this. A store of class `proven` may say it at any time: a
    store may claim less than it could, never more.

Surface names and their number are the store's own. Only the memory reference store's are fixed:
`rows`, `index-entries` (targets, negators and arrival records), `process-memory`, in that order,
with states `absent`, `absent`, `unprovable`.

### 1.6 Profile

The runner reads five things:

- `capabilities.erasure`: `proven`, `unprovable` or `none`.
- `capabilities.journal`: boolean.
- `changeRetention`: `none`, `unbounded`, or `{"revisions": n}` with n an integer of 1 or more.
  Any other value, `{"revisions": n}` with n outside 1 to 2^53 − 1 included, is a defect: the
  runner fails each `createPeer` step with the message
  `the profile's changeRetention is not none, unbounded or {revisions: n}`, before it calls the
  store.
- `pushdown.{timestampAtMost, arrivalAtMost, excludeIds}`: booleans.
- `formatVersion`: a string.

A store whose `formatVersion` equals the file's `reference.formatVersion`
(`rhizomatic.store.memory/1`) is a **memory reference store**. It is held to the extra "reference"
rules below. Its profile in slice 1 is: `values`, `journal`, `views`, `derivedIndexes`, `digest`
false; `arrival` true; erasure `unprovable`; every pushdown field true; `writers: one-process`;
`atRest: trusted`; `indexedValueRoles` empty. From slice 3 its `changeRetention` is `unbounded`,
or `{revisions: n}` when it is built to keep only n records (§3.9).

A memory reference store may be built with any subset of the three pushdown fields switched off.
It then ignores those fields and reports them not applied. **Each witness runs both files against
the reference store in all 8 subsets.** That is what exercises the residual path of the trim lemma.

## 2. Common header

`scripts.json` and `scope.json` are each one JSON object and start with the same keys.
`rounds.json` has its own header (§5.1).

```json
{
  "format": "rhizomatic-store-scripts/1",
  "note": "...",
  "reference": { "formatVersion": "rhizomatic.store.memory/1" },
  "peers": { "A": "ed25519:c3c3…", "B": "ed25519:a1a1…" },
  "deltas": [ { "name": "a-height", "id": "1e20…", "claims": { … } } ]
}
```

- `format` is `rhizomatic-store-scripts/1` or `rhizomatic-store-scope/1`. Refuse any other value.
- `peers` maps a peer name to a peer id. Steps use names. One name, `EMPTY`, maps to the empty
  string; it exists to be refused.
- `deltas` is the corpus. Steps use `name`. Fields:
  - `name`: unique in the file.
  - `id`: the content address.
  - `claims`: the JSON debug profile of [the main README](../README.md#delta--canonicalization-l0-delta).
  - `sig` (optional): a string. The delta is a signed appearance. Two entries (`short-sig`,
    `k-note-upper`) carry a malformed signature on purpose; pass the string through unchanged.
  - `forged` (optional, `true`): the `id` deliberately does not match the claims. Build the delta
    with exactly this id and these claims, without checking it. For every other entry a loader
    SHOULD check that the id recomputes.
- Two entries can share an `id` and differ in `sig`. They are two appearances of one id.

Wherever a step lists delta names for ids, the id is the named entry's `id`. Expected lists are
already in ascending id order; compare element by element.

## 3. `scripts.json`

```json
"scripts": [
  { "name": "purge", "spec": "SPEC-18 §4.7.2, §7", "requires": ["purge"], "steps": [ … ] }
]
```

Run each script on a **new, empty store**. Peer handles and snapshots live for one script.

`requires` lists what the store's profile must offer. An absent `requires` means none. A
`requires` that is present and not a list of names (`null` included) is a defect of the
document, and so is a name that is not in the table below: the script fails with a message
that names the defect, whatever the store. Skip the script, and report it as skipped, when a
requirement fails:

| Requirement | Holds when |
|---|---|
| `purge` | `capabilities.erasure` is not `none` |
| `journal-absent` | `capabilities.journal` is false |
| `changes` | `changeRetention` is not `none` |

A script lists `changes` first when it has more than one requirement, so a store without a feed
reports `changes` as what it lacks.

A step is an object with an `op`. A step passes when the store does what `expect` says.

**Refusals.** Where `expect` has an `error` key, the operation must refuse. `error` is one code,
or a list of codes:

```json
"expect": { "error": "peer-exists" }
"expect": { "error": ["posture-refused", "peer-exists"] }
```

With a list, more than one cause applies and their order is free: a refusal with any listed code
conforms. A refusal with a code that is not listed fails, and so does an answer.

### 3.1 `createPeer`

```json
{ "op": "createPeer", "peer": "A", "erasure": "unproven", "expect": { "status": "created" } }
{ "op": "createPeer", "peer": "P", "erasure": "proven",
  "expect": { "error": "posture-refused", "unlessStoreErasure": "proven" } }
```

- `{"status": "created"}`: the peer is created. Its handle reports posture `erasure` and the
  store's erasure class. Keep the handle under the name `peer`.
- `{"error": …}`: the store refuses (see "Refusals").
- With `unlessStoreErasure`: when the store's `capabilities.erasure` equals that value, the
  expectation is `{"status": "created"}` instead. No later step uses such a peer.

### 3.2 `openPeer`

```json
{ "op": "openPeer", "peer": "A", "expect": { "status": "opened", "posture": "unproven" } }
{ "op": "openPeer", "peer": "C", "expect": { "error": "peer-absent" } }
{ "op": "openPeer", "peer": "A", "handle": "A2", "expect": { "status": "opened", "posture": "unproven" } }
```

On `opened`, the handle reports that posture.

- Without `handle`, it replaces the handle kept under the name `peer`.
- With `handle`, keep the new handle under that name, and **keep the older handle** under the name
  it has. Both belong to the same peer and share one bookkeeping record (§3.3).

In `append`, `purge` and `read`, and in a scope case of `scope.json` (§4), the `peer` key is a
**handle name**. The bookkeeping is always that of the peer the handle belongs to. A peer's first handle has the
peer's own name, so most steps read the same either way. In `createPeer`, `openPeer` and `export`
the `peer` key is a name from `peers`.

### 3.3 `append`

```json
{ "op": "append", "peer": "A", "expectedHead": null, "nextHead": "head-1", "frame": null,
  "added": [ { "delta": "a-height",
               "arrival": { "at": 1001, "sequence": 1, "transfer": 1, "sender": "local" } } ],
  "expect": { "status": "committed", "added": ["a-height"], "revisionAdvanced": true } }
```

- `frame`: null, or hex bytes.
- `added[].delta`: a corpus name. The store receives that appearance.
- `added[].arrival`: the arrival record, passed to the store as written, also when a field is
  out of range (`sequence: 0`, `sequence: 1.5`, `sender: ""`, `transfer: 9007199254740992`). A
  witness whose record type cannot hold such a value answers for the store at its own boundary,
  **head first**: it reads the peer's current head; when the step's `expectedHead` differs, the
  step's answer is `conflict`; only otherwise is it the refusal `invalid-admission`. A stale
  writer gets `conflict` whatever its batch holds, in every witness. No vector combines a
  non-null `frame` with such a value, so that order stays free. Its `id` is the delta's id, unless the arrival object has
  an `id` key; then that key is a corpus name and the record carries that entry's id.
- `revisionAs` (optional, a key of the step): a revision name (§3.9). After the step, the name
  stands for the peer's revision. It appears only in scripts that require `changes`.
- `expect`, one of:
  - `{"status": "committed", "added": [names], "revisionAdvanced": bool}`. The result's ids equal
    the named ids. The result's revision equals the peer's revision after the step. That revision
    is greater than the revision before the step when `revisionAdvanced` is true, and equal when
    it is false.
  - `{"status": "conflict"}`. The revision does not change.
  - `{"error": …}`. The revision does not change.

Any other answer fails the step. That includes `uncertain`.

The runner reads the peer's revision by `read()` before and after the step.

**Bookkeeping.** For each peer the runner remembers which appearance and which arrival record each
held id was admitted with: on `committed`, for each id in the result, the first entry of `added`
with that id. A purge forgets every id in its report's `targets`, whatever the outcome: after
`removed` and after `held-by-other-peer` the peer holds the id no longer, and after the other
outcomes it held nothing to forget. So an id appended again is checked against its new arrival
record. Later steps check store answers against this record.

### 3.4 `purge`

```json
{ "op": "purge", "peer": "A", "ids": ["a-height-neg", "a-height", "far"],
  "expect": {
    "targets": [ { "delta": "a-height-neg", "outcome": "removed" },
                 { "delta": "a-height", "outcome": "held-by-other-peer" },
                 { "delta": "far", "outcome": "not-held" } ],
    "revisionAdvanced": true,
    "claim": { "unprovable": "unproven", "proven": "proven" },
    "referenceSurfaces": [ { "surface": "rows", "state": "absent" },
                           { "surface": "index-entries", "state": "absent" },
                           { "surface": "process-memory", "state": "unprovable" } ] } }
```

`revisionAs` (optional) names the peer's revision after the step, as in §3.3.

`expect.claim` is one of two objects: `{"unprovable": "unproven", "proven": "proven"}` when a
target is `removed`, and `{"unprovable": "nothing-removed", "proven": "nothing-removed"}` when
none is. A `claim` with any key other than `unprovable` and `proven`, or without one of them, is
a defect of the document: the step fails, whatever the store answers.

A `claim` has no entry for class `none`. A store of class `none` refuses every purge (§1.3), and
every script that purges requires `purge`, so the runner skips it for such a store. If a store
of class `none` reaches a purge step anyway, the step fails: there is no expectation for it. The
refusal itself is a test of each witness (§7, test 8), not a rule of the runner.

Checks:

- The purge answers. A refusal fails the step.
- The report's `targets` equal `expect.targets`, in order, by id and outcome.
- The report's `revision` is the peer's revision after the step; `revisionAdvanced` as in §3.3.
- `boundary` is `store-controlled-surfaces`.
- Let E be `expect.claim[<the store's erasure class>]`. The report's `claim` must equal E, with
  one exception: where E is `proven`, `unproven` also conforms. Nothing else is exchanged: `proven`
  never conforms where E is `unproven` or `nothing-removed`, and `unproven` never conforms where E
  is `nothing-removed`.
- Every surface state is one of the three values.
- If `claim` is `proven`: the surface list is not empty and every state is `absent`.
- **Reference:** a memory reference store's `surfaces` equal `referenceSurfaces` exactly, in order.

### 3.5 `read` and `release`

```json
{ "op": "read", "peer": "A", "snapshot": "s1" }
{ "op": "release", "snapshot": "s1" }
```

`read` takes a snapshot of the peer and keeps it under the name `snapshot`, with the peer it
belongs to. `release` releases it. Neither has an `expect`.

### 3.6 Snapshot fields: `head`, `count`

```json
{ "op": "head", "snapshot": "s", "expect": { "head": "head-1" } }
{ "op": "count", "snapshot": "s", "expect": { "count": 7 } }
```

These read the values fixed when the snapshot was read. They never refuse, also not on a moved or
released snapshot.

### 3.7 Queries: `get`, `arrivals`, `targets`, `negators`, `scope`

```json
{ "op": "get",      "snapshot": "s", "ids": ["a-name", "ghost"], "expect": { "deltas": ["a-name"] } }
{ "op": "arrivals", "snapshot": "s", "ids": ["a-name", "ghost"], "expect": { "ids": ["a-name"] } }
{ "op": "targets",  "snapshot": "s", "entities": ["plant:a"],    "expect": { "ids": ["a-name", "a-height"] } }
{ "op": "negators", "snapshot": "s", "ids": ["a-height"],        "expect": { "ids": ["a-height-neg"] } }
{ "op": "scope",    "snapshot": "s",
  "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
  "pushdown": { "timestampAtMost": 30, "arrivalAtMost": 4, "excludeIds": ["a-name"] },
  "exclude": ["a-height"],
  "expect": { "lower": ["a-height-neg"], "upper": ["a-name", "a-height-neg", "a-height"] } }
```

Ask the store first and judge the answer afterwards: a store that answers where the step expects
a refusal fails for that, whatever it answered.

`expect` is one of three shapes:

1. A result, as below. The operation must answer, and the answer must match.
2. A result with `"orError": "snapshot-moved"`. The operation either refuses `snapshot-moved`, or
   answers and the answer matches. Any other answer or refusal fails.
3. `{"error": …}`. The operation must refuse (see "Refusals"). A snapshot that is both released
   and moved carries `["snapshot-released", "snapshot-moved"]`.

Result checks:

- `get`: the returned ids equal the named ids. Each returned delta is the **named appearance**:
  same id, same `sig` (absent when the entry has none), and claims that recompute to the id.
- `arrivals`: the returned records' ids equal the named ids. Each record equals the one the
  runner's bookkeeping holds for this peer and id, field by field.
- `targets`, `negators`: the returned ids equal the named ids.
- `scope`: `pushdown` and `exclude` are optional; their id lists are corpus names. A bound is
  passed as written, also when it is out of range (`arrivalAtMost: 1.5`, `-1`,
  `9007199254740992`); a witness whose type cannot hold the value refuses `invalid-request` at its
  own boundary. A witness whose type can hold the value MUST pass it to the store: its runner
  does not answer for the store. Then:
  - R is ascending by id with no id twice.
  - Every member of R is held by the snapshot's peer per the bookkeeping, has claims that
    recompute to its id, carries the signature of the appearance that peer admitted, and carries
    that peer's arrival record.
  - `applied` reports no field that was not requested.
  - Every id of `lower` is in R. Every id of R is in `upper`. Here `lower` is
    `S(A over H_p) \ exclude` and `upper` is `S(A over H)`. This `upper` is the loose bound; the
    exact upper bound of §1.4.1 is checked in `scope.json`.
  - **Reference:** a memory reference store reports `applied[f]` true exactly for each requested
    field whose profile entry is true. When it applied every requested field, R equals `lower`.

### 3.8 Export

```json
{ "op": "export", "peer": "A", "expect": { "deltas": ["b-name", "a-height"] } }
{ "op": "export", "peer": "C", "expect": { "error": "peer-absent" } }
{ "op": "exportStored", "expect": { "ids": ["b-name", "a-height", "far"] } }
{ "op": "exportPeers", "expect": { "peers": ["B", "A"] } }
```

- `export`: `admin.peer(peer).ids()` equals the named ids. `admin.peer(peer).deltas()` yields the
  same count, and each is the named appearance (as `get`). A refusal may come when the listing is
  read.
- `exportStored`: `admin.storedIds()` equals the named ids. An id two peers hold appears once.
- `exportPeers`: `admin.peers()` equals the ids of the named peers, in the listed order.

### 3.9 The change feed

A store whose `changeRetention` is not `none` serves a change feed (SPEC-18 §4.6, §4.13). The
runner checks it in two ways: by its own model after **every** step of every script and of the
`scope.json` setup, and by `changes` steps in the scripts that require `changes`. A store whose
retention is `none` gets neither: the runner skips the scripts that require `changes` and makes
no feed check.

#### 3.9.1 The operation

`peer.changes(from, to?)` answers `{"status": "ok", "records", "through"}` or
`{"status": "resync-required", "current"}`, or refuses. A record is
`{revision, head, added, removed}`. SPEC-18 §4.6 states the rules. In short:

- One record per revision advance, and no other. Its `head` is the peer's head after the commit.
  `added` is what the commit newly held. `removed` is what left the peer's holdings at that
  commit; a settled debt is not in it. Both are ascending by id, with no id twice.
- A page answers the records with `from < revision ≤ through`, ascending, with none missing.
  `through` is at most the clamped `to` (the clamped `to` is `to`, or the current revision when
  `to` is absent or later). When the page holds the whole range, `through` is the clamped `to`.
  Otherwise `through` is the revision of its last record, greater than `from`.
- **The order of the answers.** (1) A `from` or `to` that is not an integer from 0 to 2^53 − 1
  is refused `invalid-request`. (2) An explicit `to` below `from` is refused `invalid-request`.
  (3) Then the answer is `resync-required` exactly when `from` is below the floor or above the
  current revision. (4) Otherwise it is `ok`. A defaulted `to` is never compared with `from`, so
  a cursor from the future with no `to` gets `resync-required`.
- `current` in a `resync-required` answer is the peer's current revision.
- **The floor** is the revision of the newest record the store dropped, or the peer's revision at
  creation when it dropped none. A `from` at or above the floor and not above the current
  revision answers `ok`. Where revisions advance by one, the floor is also the revision just
  before the oldest kept record. Where they skip values, a `from` between the newest dropped
  revision and the oldest kept one is above the floor.
- **Shape.** A record has exactly the keys `added`, `head`, `removed`, `revision`. An `ok` answer
  has exactly `records`, `status`, `through`. A `resync-required` answer has exactly `current`,
  `status`. Any other key fails, with the messages of §3.9.3. A typed witness whose record and
  page types have exactly these fields meets this rule by construction; it names the rows it
  cannot reach in its rule-table file (§8). An adapter that decodes a serialized answer (a
  remote store, a store over another language) MUST refuse a field it does not know.
- **Ownership.** A caller may change anything an answer returned: its list of records, a record,
  a record's `added` or `removed` list. No later answer changes (§7, test 9).

#### 3.9.2 The runner's model

For each peer, the runner keeps:

- `revisions`: the peer's revision when it was created, read with `read()` right after
  `createPeer`, and then the revision after each step that advanced it.
- `records`: one expected record per advance.
- `head`: the peer's head, null at first.
- `everHeld`: every id the peer has held.
- `seen`: each record as the store first returned it, by revision.

It updates the model on these steps, after the step's own checks:

- `append` that answers `committed`: `head` becomes `nextHead`, and the result's ids join
  `everHeld`. When the revision advanced, append the revision after the step to `revisions` and
  the record `{revision: <after>, head: nextHead, added: <the step's expected ids>, removed: []}`
  to `records`.
- `purge` whose revision advanced: append the revision after the step, and the record
  `{revision: <after>, head: <the model's head>, added: [], removed: R}`. R is the report's
  targets, in order, that the bookkeeping of §3.3 held when the purge began. The outcome alone
  does not decide: `removed` is also the outcome of a settled debt.

Let keep be infinite for `unbounded` and n for `{revisions: n}`. The peer keeps the last keep
records of `records`. Let i be the number of records it dropped (`records.length − kept`). The
**floor** is `revisions[i]`: the revision at creation when nothing was dropped, and otherwise the
revision of the newest dropped record. This is the floor of §3.9.1; the runner does not use
"the revision just before the oldest kept record", which differs where revisions skip values.

**Messages.** In §3.9.3 to §3.9.6 the fixed words of each message are normative. How a value
inside a message is rendered is each witness's own: an id in full or shortened, a head, a list
of ids or of revisions. Each witness's rule table pins its own rendering. Below, `<…>` marks a
rendered value.

#### 3.9.3 The check of each commit

After every `append` (committed, `conflict` or refused) and every `purge`, let `before` be the
revision read before the step. Through the step's own handle, call `changes(before)` with no
`to`, and again from each `through`, until a page
has `through` at or past the current revision or makes no progress. Each page must answer: a
refusal fails with `changes refused with <code>`. Then each answer's shape is checked, here and
wherever the runner reads an answer of `changes`:

- An answer whose `status` is `resync-required` has exactly the keys `current`, `status`, else
  `a resync answer has the keys <k>, not current, status`.
- An answer whose `status` is `ok` has exactly `records`, `status`, `through`, else
  `a change page has the keys <k>, not records, status, through`. `records` is a list, else
  `a change page's records is not a list`. Each record has exactly `added`, `head`, `removed`,
  `revision`, else `a change record has the keys <k>, not added, head, removed, revision`.
- `<k>` lists the answer's own keys, sorted by UTF-16 code unit and joined by ", ". A value that
  is not an object fails with `a <what> is not an object`. An answer with another `status` is
  not checked here.

A page that is not `ok` then fails with `changes from the revision before a commit is not ok`.
Then, over the records collected:

1. Every id they name is in `everHeld`, else
   `the feed of <peer> names <id>, which <peer> never held`.
2. Each record's `added` and `removed` are ascending and distinct, else
   `a record's ids are not ascending and distinct`.
3. When the revision did not advance: there is no record, else
   `a step that did not advance the revision wrote a record`.
4. When it advanced to R: there is at least one record, else
   `the head-only commit to revision R wrote no record` (when the expected record has no id) or
   `the commit to revision R wrote no record`. Then there is exactly one, at revision R, else
   `the commit to revision R wrote records at <revisions>`. Its head, `added` and `removed`
   equal the expected record's, else, in this order:
   - `the record of revision <R> has head <head>, expected <head>`;
   - `the record of revision <R> adds <ids>, expected <ids>`;
   - `the record of revision <R> removes <ids>, expected <ids>`.

The check of each commit does not record what it reads as "seen" (§3.9.5, check 13): only a
page read does.

#### 3.9.4 The check after every step

After every step of every script, and of the `scope.json` setup, for each peer the run created:
let F be the floor. Read the pages from F with no `to` (§3.9.5); an answer of `resync-required`
fails with `changes answered resync-required from F, and every record after F is retained`. When
the peer dropped records (i > 0):

1. **Below the floor.** Make ONE call `changes(revisions[i − 1])`, with no `to` and no paging.
   A refusal fails with `changes refused with <code>`. Check the answer's shape (§3.9.3). It
   must answer `resync-required`, else
   `changes answered ok from <r>, below the retention floor <F>`. Its `current` must be the
   model's current revision, else
   `a resync answer carries current <c>, not the peer's revision <r>`.
2. **Between the floor and the revision before it.** Let p be `revisions[i − 1]` and n = F − p − 1,
   the number of integers strictly between them. Ask at these `from` values, ascending: every
   integer in (p, F) when n ≤ 24; otherwise p + 1 to p + 8, then p + 9 + floor(k × (F − p − 19)
   / 7) for k = 0 to 7, then F − 8 to F − 1 (24 values, all distinct). At each, make the same one
   call, with the same checks and messages. Only a store whose revisions skip values reaches it:
   there each such `from` is not a revision the peer had, and it is still below the floor.
   Probing F − 1 alone is not enough: a store can be right there and wrong at F − 2 (§8, the
   rows "ok two below the floor"). The bound keeps a store whose revisions are 1000 apart cheap.
3. **The floor probe.** Let K be `revisions[i + 1]`, the revision of the oldest kept record.
   When F + 1 < K, read the pages from F + 1 with no `to` (§3.9.5). An answer of
   `resync-required` fails with `changes answered resync-required from <F + 1>, above the
   retention floor F`. Only a store whose revisions skip values reaches this probe.

The check after every step reads through the handle kept under the peer's own name (§3.2).

#### 3.9.5 Reading pages

To read the pages from `from` to `to` (`to` may be absent), let `current` be the model's last
revision and `end` the smaller of `to` and `current` (`current` when `to` is absent). Starting at
`at = from`, call `changes(at, to)` and check the answer, in this order:

1. It answers. A refusal fails with `changes refused with <code>`. Then its shape is checked
   (§3.9.3), before its status is read.
2. `resync-required`: on the first page this ends the read with that answer, and `current` must
   be the model's current revision, else
   `a resync answer carries current <c>, not the peer's revision <r>`. On a later page it fails
   with `changes answered resync-required in the middle of a range`.
3. Not `ok`: `changes answered neither ok nor resync-required`.
4. Every id the records name is in `everHeld` (the message of §3.9.3, check 1).
5. The records are ascending by revision, strictly: `the page's records are not ascending by
   revision`.
6. Each record's revision is in `(at, end]`: `a record lies outside the range (at, end]`.
7. Each record's ids are ascending and distinct (§3.9.3, check 2).
8. Let `last` be the last record's revision, or `at` when there is none. `through` is in
   `[last, end]`, else `the page's through T lies outside [last, end]`.
9. Every model record in `(at, last]` is in the page, else
   `the feed has no record for revision R`. The model here is every record the peer ever
   wrote, dropped ones included; checks 10 and 13 use the same model.
10. No model record is in `(last, through]`, else
    `the page claims through T and leaves out the record at R`.
11. `through > at`, or `at = end`: else `the page from <at> made no progress toward <end>`.
12. `through` is `last` or `end`, else
    `the page's through T is past its last record and short of <end>`.
13. For each record: if a page read returned a record at that revision before, it is equal,
    else `the record at revision R changed after it was written`. Then it equals the model
    record at that revision, else `the record at revision R differs from its commit`. Each page
    read, the asking again of check 14 included, records what it returned as "seen"; the check
    of each commit (§3.9.3) and the calls below the floor (§3.9.4) do not.
14. **Ownership.** Copy the page's records for the result. Then change what the store returned,
    each change in its own attempt; a change that throws (a frozen value) is ignored:
    push onto the page's list of records a copy of its first record with `head` `"tampered"`
    (when it has a record); then, for each record, set `head` to `"tampered"`, push `"tampered"`
    onto `added`, and push `"tampered"` onto `removed`. Call `changes(at, to)` again. A refusal
    fails with `changes refused with <code>`. Check the answer's shape (§3.9.3). It must answer
    `ok`; every record it returns that shares a revision with a record of the first answer must
    equal that record, field by field; and no two records may share a revision. Else
    `changes answered differently after the caller changed what it returned`. The second
    answer may be another prefix of the range (§4.6 lets a store return any prefix): it may
    hold more or fewer records than the first. Then checks 4 to 13 run on the second answer
    too, from the same `at`.

Collect the copies. When `through` is `end`, the read is done. Otherwise set `at = through` and
call again.

#### 3.9.6 `mark`, revision names and `changes` steps

```json
{ "op": "mark", "peer": "A", "as": "middle" }
{ "op": "changes", "peer": "A", "from": { "revision": "A.1" }, "to": { "revision": "A.10", "ahead": 3 },
  "expect": { "status": "ok", "records": [
    { "revision": "A.7", "head": "head-7", "added": [], "removed": [] } ] } }
{ "op": "changes", "peer": "A", "from": { "revision": "A.10", "ahead": 1 },
  "expect": { "status": "resync-required" } }
{ "op": "changes", "peer": "A", "from": { "revision": "A.3" }, "to": { "revision": "A.1" },
  "expect": { "error": "invalid-request" } }
```

- A **revision name** stands for one revision of one peer. `mark` names the peer's current
  revision, read with `read()`. `revisionAs` on `append` and `purge` names the revision after the
  step. In the feed scripts every peer's revision at creation is named `<peer>.0` by a `mark`,
  and every advance `<peer>.<k>` by `revisionAs`; the k are the model's, so a store's own
  numbers need not match them. `peer` is a handle name (§3.2); the name belongs to that handle's
  peer.
- A **revision reference** is `{"revision": <name>}`, or with `"ahead": k`: the named revision
  plus the integer k. The vectors use `ahead` only to reach past the current revision. An
  `ahead` that is not an integer of 0 or more (negative or fractional) is a document defect:
  `the vector's ahead is not a whole number`.
- Document defects, whatever the store: a name used before it is given
  (`the vector names an unknown revision <name>`), a name of another peer
  (`the vector names revision <name> of another peer`), and a name given twice
  (`the vector names revision <name> twice`). A `mark` on a peer not yet created fails with
  `the vector uses peer <peer> before creating it`. A `changes` step that is not a refusal, on a
  store without a feed, fails with `a changes step on a store that serves no feed`.

A `changes` step resolves `from` and `to` to integers and then:

- `{"error": …}`: one call `changes(from, to)`, which must refuse with a listed code. No paging.
- Otherwise the step expects `resync-required` when `expect` says so, **or when `from` is below
  the floor** (§3.9.2): a document is written for a feed that keeps every record, and a store
  that keeps fewer answers `resync-required` there. Read the pages (§3.9.5) from `from` to `to`,
  with all their checks, first. Then give the verdict below.
  - Expected `resync-required`, answered `ok`: fail with
    `changes answered ok from <from>, below the retention floor F` (when `from` is below F) or
    `changes answered ok from <from>, and the step expects resync-required`.
  - Expected `ok`, answered `resync-required`: fail with
    `changes answered resync-required from <from>, and every record after <from> is retained`.
  - Expected `ok`: the records collected equal `expect.records`, with each revision name
    resolved and each corpus name turned into its id, else
    `changes answered the records of <revisions>, expected <revisions>`.

#### 3.9.7 The runs each witness makes

Run both files against the reference store:

1. As built by default (every record kept, no page limit). This run is the one the 8 pushdown
   subsets of §1.6 use.
2. Keeping two records (`{revisions: 2}`), and keeping one.
3. With pages of one record. Every range of two or more records then takes more than one page;
   `feed-appends-and-head-only-commits` reads ten records from `A.0`.
4. Keeping two records, with pages of one record.

Every run passes and skips nothing. A witness whose store has no page limit runs 1 and 2.

#### 3.9.8 What the feed scripts hold

- `feed-appends-and-head-only-commits`: plain appends; a head-only commit, and a head move with a
  held id; a no-op append; a refused append and a `conflict` (no record); ten records, read
  whole, from a mark, as a range, as one record and as nothing; `from = to`; `from` equal to the
  current revision; a `to` clamped; `to < from`, also from the future; a cursor from the future,
  with and without a `to`.
- `feed-purge-and-debts`: a purge that releases a held id and an id another peer holds (both in
  `removed`); purges of an owed id, of an id never held, and an empty purge (no record); a purge
  that settles a debt and releases another id (only the second in `removed`); an id added,
  purged and added again; three peers.
- `feed-a-debt-ends-on-append`: an append that ends a debt adds the id again; a later purge
  releases it again.
- `feed-two-peers-interleaved`: two peers committing in turn, sharing bytes, through two handles
  of one peer. Each feed names only its own peer's ids, and each peer's revisions are its own.

#### 3.9.9 The cost rails

The vectors cannot measure cost. Each witness times two rails from outside, with a monotonic
clock, in the manner of §6 "Building `scopeSource`": N from 256, doubling until the run takes
50 ms; the run at N the fastest of five; the run at 8N the fastest of three, stopping at the
first under the bound; the ratio of the two below 24. A witness may measure a slow rail again,
up to three measurements in all, and fail it only when every one reaches 24; a quadratic store
reaches it every time. The Rust witness does so, and runs its timed rails one at a time.

1. **A window read after each record.** Build a peer with N + W head-only commits (W = 64 in the
   TypeScript witness). Time N calls: call r reads `changes(r, r + W)` and gets W records. A store
   that walks its feed from the start to find `from` does quadratic work in total.
2. **Appends under bounded retention.** On a store that keeps N / 4 records, time N head-only
   appends. A store whose drop copies or shifts what it keeps does quadratic work in total.

Each witness measures each rail red once: against a store that finds `from` by walking the
feed, and against one whose drop copies the kept records. In the TypeScript witness the first
measured a ratio of 83 and the second 267.

## 4. `scope.json`

```json
{
  "format": "rhizomatic-store-scope/1", "note": "…", "reference": { … }, "peers": { … },
  "deltas": [ … ],
  "setup": [ <steps> ],
  "cases": [
    { "name": "signed-time-cuts-a-chain", "spec": "SPEC-18 §4.3", "peer": "A",
      "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
      "selection": { "timestampAtMost": 30 },
      "held": [],
      "scopes": [ { "fields": [], "ids": [ … ] },
                  { "fields": ["timestampAtMost"], "ids": [ … ] } ] }
  ]
}
```

Open **one** new store. Run `setup`: steps in the §3 format, with the same checks and bookkeeping.
Then run every case against that store. Cases only read.

A case:

- `selection`: the read's whole selection, in pushdown form (§1.4.1). Its present fields are P.
- `peer`: a handle name (§3.2). The setup opens a second handle of one peer, and one case reads
  through it.
- `held`: ids the read already holds. The peer holds all of them. They stand for what earlier
  rounds of the **same read on the same snapshot** fetched. The lemma does not hold for deltas
  held from another snapshot.
- `scopes`: one entry for **every subset** f of P (2^|P| entries). `fields` lists f in the fixed
  order `timestampAtMost`, `arrivalAtMost`, `excludeIds`. `ids` is `S(A over H_f)`: the scope when
  only the fields of f select.
- The entry with `fields` = P is the **exact scope** of the read.

For each entry f of `scopes`, on one snapshot of `peer`:

1. Call `scope` with the anchors, `exclude` = `held`, and `pushdown` = the fields of `selection`
   that are in f. Omit `pushdown` when f is empty.
2. Check R as in §3.7: ascending, held, right appearance, right arrival record.
3. Let q be the fields reported applied. q ⊆ f, else fail.
4. **Lower bound:** every id of `scopes[f].ids` that is not in `held` is in R.
5. **Upper bound:** every id of R is in `scopes[q].ids`.
6. **Reference:** a memory reference store reports q = f restricted to the fields its profile
   offers, and R equals `scopes[q].ids` minus `held` exactly.
7. **Trim lemma.** The host's residual selection is the fields of P not in q. Build the set
   D′ = (members of R that pass the residual fields) ∪ (the held deltas of `held`, with the
   arrival records from the bookkeeping, that pass every field of P). The held deltas are the
   appearances the peer admitted: a runner takes them from its bookkeeping, or reads them with
   `get` on the same snapshot. Compute S(A over D′) in the runner. It MUST equal the exact scope.

Step 7 is the lemma: whatever the store applied, the host reaches the same scope from R and what
it already holds. A store that reports an applied field but returns members that fail it breaks
step 5. A store that drops a member the selection keeps breaks step 4.

## 5. `rounds.json`

This file pins the store-backed read of SPEC-18 §4.4: an anchored read (SPEC-17 §5, §6) that
fetches its scope from one snapshot, one round at a time, and evaluates in memory between
rounds. The rule it holds a reader to: **a read in rounds answers the same bytes as the same
term evaluated over everything the peer holds that the selection admits.**

Every expectation is computed over plain lists. The holdings are an array, the selection is a
filter over it, the answer is the ordinary evaluator over what the filter keeps, and each scope
is found by scanning (§1.4.1's two steps). No expectation comes from a store or from a
store-backed read.

### 5.1 The document

```json
{
  "format": "rhizomatic-store-rounds/1", "note": "…",
  "deltas":  [ { "name": "g-name", "id": "1e20…", "claims": { … } } ],
  "schemas": [ { "name": "Tree3", "alg": 1, "body": <term> } ],
  "load": { "peer": "ed25519:5a5a…", "erasure": "unproven",
            "admissions": [ { "expectedHead": null, "nextHead": "rounds-head-1",
                              "added": [ { "delta": "c1-height-neg-neg",
                                           "arrival": { "at": 1001, "sequence": 1,
                                                        "transfer": 1, "sender": "rounds" } } ] } ] },
  "cases":       [ <case> ],
  "interleaved": [ <interleaved case> ],
  "refusals":    [ <refusal> ]
}
```

- `format`: refuse any other value.
- `deltas`: the corpus, as in §2 (`name`, `id`, `claims`). No entry is signed and none is forged;
  a loader checks that each id recomputes.
- `schemas`: hyperschemas, in the form the `l1-eval` vectors use. Build one registry from all of
  them. `body` and every `term` below are term JSON ([the main README](../README.md)).
- Wherever a list names deltas, it holds corpus names, and the ids are in ascending id order.
  Entity lists are ascending by UTF-8 bytes.

### 5.2 The load rule

For each run that needs a loaded peer, on a **new** store:

1. `createPeer(load.peer, { erasure: load.erasure })`.
2. For each entry of `load.admissions`, in order: `append` with `expectedHead` and `nextHead` as
   written, `frame` null, and `added` in the order written. Each entry of `added` is the named
   delta with the arrival record written beside it; the record's `id` is the delta's id. Every
   append MUST answer `committed`.

After the load the peer holds every delta an admission names. The corpus also has deltas that no
admission names; only an interleaved case appends them (§5.5). Arrival order is not signed-time
order, on purpose.

### 5.3 What the reader under test does

Names here are neutral; a witness spells them its own way. The reader takes a snapshot, a term,
a root, `now`, optional bindings and a selection, and works as follows.

1. **Classify.** Run the SPEC-17 §5 anchor analysis of the term, with the bindings. An unanchored
   term is refused with the analysis reason, **before any store call** (§5.6). Taking a snapshot
   is a store call: a reader that opens its own snapshot refuses before it opens one.
2. **First anchors.** The request root and the term's static anchors, as a set, ascending.
3. **One round.**
   1. Make **one** `scope` call (§1.4.1). `anchors` is exactly the entities no earlier round
      asked for. `pushdown` is the selection. `exclude` is every id the read holds from earlier
      rounds, in any order; it may be omitted when the read holds nothing.
   2. Add every returned delta to the **fetch cache**, with its arrival record. The cache keeps
      a delta that fails the selection: the next round's `exclude` names it, so the store does
      not send it again. The cache owns what it holds, as a store does (§1, §7): it checks and
      copies each member, computes the id over its copy, and refuses `invalid-request` for a
      member that is malformed, whose id does not recompute, or whose arrival record is
      missing or names another id. A refused call adds nothing.
   3. Compute the **exact members**: S(E over C′), where E is every anchor asked for so far, C
      is the cache, and C′ is the members of C that pass the **residual selection**. The
      residual is each selection field that some round's answer did not report applied, plus any
      selection the host did not push down at all. S is §1.4.1's two steps, over C′.
   4. Evaluate the gather over exactly those members, at the root, at `now`. The gather is the
      term, or the operand of the term when the term is a `resolve`.
   5. The **next anchors** are the anchors the result shows (its root and every expanded child,
      at any depth) that no round has asked for, ascending. When there are none, the read ends.
4. **The answer.** The result of the term over the last round's members (for a `resolve` term,
   one more evaluation of the whole term over the same members). With it: the **scope** (every
   anchor asked for), the **members** (the last round's exact members) and the snapshot's
   revision.

All rounds use one snapshot. A reader makes no store call other than the one `scope` per round:
no `get`, `targets`, `negators` or `arrivals`.

Why step 3.1 may ask for the new anchors only: S(A ∪ B) = S(A) ∪ S(B), and the store follows
negation chains through `exclude` (§1.4.1). Why step 3.3 is exact: the trim lemma of §4.

### 5.4 A case

```json
{ "name": "every-field", "note": "…",
  "term": <term>, "root": "garden:1", "now": 100,
  "bindings": { "who": "plant:s" },
  "selection": { "timestampAtMost": 60, "arrivalAtMost": 38, "excludeIds": ["b1-has-p1"] },
  "expect": { "canonicalHex": "a2…",
              "scope": ["bed:1", "bed:2", …],
              "members": ["c2-tag-neg-at-b1", …],
              "rounds": [ { "anchors": ["garden:1"] }, { "anchors": ["bed:1", "bed:2", "plant:s"] } ] } }
```

- `bindings` (optional): hole name to primitive, the request's bindings.
- `selection`: the read's whole selection in pushdown form (§1.4.1). `excludeIds` holds corpus
  names. An empty object selects everything.
- `expect.canonicalHex`: the canonical bytes of the result (the HView, or the View of a `resolve`
  term), lowercase hex, as the `l1-eval` vectors encode a result.
- `expect.scope`: every anchor of the read, ascending.
- `expect.members`: the exact members when the read ends, S(scope) over the admitted holdings.
- `expect.since` and `expect.expiresAt`: the validity window of the read's operand at `now`
  (SPEC-18 §4.6). Over the deltas of `expect.members`, `since` is the greatest `validFrom` or
  `validUntil` at or before `now`, and `expiresAt` the least strictly after it; each is null when
  there is none.
- `expect.rawMembers`: the raw scope of `expect.scope`, S(scope) over everything the peer holds
  with no selection: the members of the read's capture. It differs from `members` exactly where
  the selection trims.
- Four cases (`the-whole-garden-at-55`, `signed-time-cuts-a-link-and-a-strike-at-55`,
  `arrival-cuts-a-strike-so-a-child-appears-at-55`, `a-resolved-tree-at-55`) repeat a read at
  `now` 55, inside the fixture's boundaries. Their window is closed at both ends.

Modes 2 to 5 read with a capture asked for, and MUST give `since`, `expiresAt` and `rawMembers`
(the capture's members). Mode 1 computes the window over the members it found by scanning, and
`rawMembers` by scanning everything held. A witness that does not yet carry the window or a
capture on a read skips these three fields and says so. Both witnesses carry them.

**The same read, five ways.** A witness evaluates each case in each mode below, on a peer loaded
by §5.2. Every mode MUST give `canonicalHex`, `scope` and `members`.

| # | Mode | How |
|---|---|---|
| 1 | Whole surface | List the peer's deltas through the exporter (`openAdmin().peer(id).deltas()`), keep those that pass `selection`, evaluate the term over all of them with the ordinary evaluator. The exporter lists no arrival record: take each delta's arrival from the load (§5.2). The scope is the request root, the term's static anchors, and the anchors that the gather's HView shows when the gather is evaluated over the same deltas (for a `resolve` term the gather is its operand; the View itself shows no anchors). The members are the scope of those entities, found by scanning. |
| 2 | Rounds, no cache | §5.3, but every round asks for **every** anchor so far and sends no `exclude`. Each answer alone then carries the whole scope so far; nothing an earlier round fetched is needed. |
| 3 | Rounds, fetch cache | §5.3 as written. |
| 4 | Rounds, evaluation memo, no fetch cache | Mode 2 with the memo below. |
| 5 | Rounds, both caches | Mode 3 with the memo below. |

Modes 4 and 5 exist once a witness has the evaluation memo; until then it runs 1 to 3.

**The evaluation memo** (SPEC-18 §4.4; §4.12 readings 21 to 26 give the proof). A **child
evaluation** is one schema body evaluated at one root: each child of an `expand`, and the body of
a `fix`. The memo works as follows.

1. One memo per attempt of one read. It starts empty when the read takes its snapshot. A read that
   starts again on a new snapshot starts a new memo. No memo serves two reads.
2. The key is (schema reference, bindings, root). The schema reference is the name or the pinned
   hash, as the term writes it. The bindings are the ones in effect: the request's, or those of
   the nearest enclosing `fix` that has `bindings`. Compare them by identity within the read (one
   object, or one place in the term) or by content, entry by entry (a number by its bits); two
   binding sets with the same entries may share a key or not. Two binding sets that differ in any
   entry must never share a key. The root is the entity id.
3. Before it evaluates a child, the evaluator looks up the key. On a hit it uses the stored HView
   and evaluates nothing under that child.
4. After it evaluates a child, it stores the HView only when the child is **final**: every anchor
   the HView shows has been asked for in this read, in this round or an earlier one. The anchors
   an HView shows are its id and the id of every child expanded inside it, at any depth (the same
   set as step 3.5 of §5.3). A child that is not final is not stored; the next round that reaches
   it evaluates it again.
5. The final `resolve` evaluation of a `resolve` term uses the same memo.
6. When an evaluation budget is present, the memo is off: no lookup and no store. A hit would skip
   the work the budget counts. A store-backed read has no budget.

The memo changes no answer, no scope, no member and no round: modes 4 and 5 have the same round
anchors as modes 2 and 3.

Mode 1's scope equals the scope of the rounds. SPEC-17 discovery finds only true anchors, so the
whole-surface gather shows exactly the anchors that the rounds reach, and no others.

`expect.rounds` is **normative for modes 3 and 5**: the number of `scope` calls and the anchors
of each. In modes 2 and 4, round i asks for the union of `rounds[0..i]`.

**Every pushdown profile.** Run every case, in every mode, against the memory reference store
with each of the 8 subsets of pushdown fields switched off (the same 8 profiles as §4 and
SPEC-18 §4.11 reading 25). A switched-off field comes back unapplied, and the reader's residual
selection (§5.3 step 3.3) must do its work, inside a read of several rounds.

What the fixture holds, so a reader that gets one of these wrong fails a case:

- Expansion of depth three: four rounds from `garden:1`.
- `g-features-c1` points at the root and at `cutting:1`: fetched in round 1, filed at an anchor
  of round 3, with a negation of a negation fetched beside it.
- `plant:s` is a child of the garden and of both beds, and `cutting:1` of two plants. `seed:1`
  is reached only through the garden's own link to `plant:s`.
- `c2-tag-neg-at-b1` is a negation that points at `bed:1`. Round 2 fetches it and its own
  negation; its target arrives in round 3.
- `b1-late-note-neg-at-c2` is signed before its target and points at `cutting:2`. Under
  `timestampAtMost: 60` its target is gone: it is no member through `bed:1`, and it is a member,
  negated, through `cutting:2`. A store that leaves the field to the host returns it in round 2;
  round 3 then owes its negation though the read already holds it.
- A chain of three negations at `cutting:2`, with a selection that drops its first link and one
  that drops its middle link.
- A child link that is negated (`b2-has-p2`), whose negation arrives late: `arrivalAtMost`
  uncovers a child and changes the rounds. A link signed late (`p1-has-c3`): `timestampAtMost`
  removes an anchor.
- A static anchor (`grants`) in round 1, a hole bound by the request, a `resolve` term, a root
  nothing points at, and a selection that admits nothing.
- A `resolve` term under each pushdown field (`a-resolved-tree-*`). Each selection changes the
  View, so a reader that evaluates the final `resolve` over everything it holds, and not over
  the members, fails under a profile that leaves the field to the host.
- A member on each bound. `c1-note-neg-by-carol` has timestamp 44 and arrival sequence 30, and
  the two cuts there keep it (`timestamp <= timestampAtMost`, `sequence <= arrivalAtMost`). A
  strict comparison drops it, and `c1-note` shows.
- Two index shapes: `b2-name-twice` points at `bed:2` twice, and `c2-size-remark` points at
  `c2-size` with the role `annotates`, which is no negation.
- One child under two bindings (`one-child-under-two-bindings`). `StrikerLeaf` trusts the
  strikes of the author that the hole `striker` names. The `fix` reads the tree with Alice's
  strikes; the `expand` over it follows the garden's `star` link to `cutting:1` with the request's
  bindings, Bob's. Round 2 reaches `cutting:1` under `StrikerLeaf` both ways, and both are final
  in that round. The two HViews differ: under Bob's strikes `c1-height` is struck. A memo whose
  key leaves out the bindings serves one for the other and fails this case, and only this case.
- One child under two pinned schemas (`one-child-under-two-pinned-schemas`). `RoleLeaf` is
  `Leaf` filed by role, not by context. Two `expand`s follow the `child` links of `plant:s`, one
  under `Leaf` and one under `RoleLeaf`, and each names its schema by its pinned hash. Round 2
  reaches `cutting:1` and `cutting:2` under both, and all four children are final in that round.
  At each entity the two HViews differ. A memo whose key does not tell two pinned references apart
  serves one for the other and fails this case.

### 5.5 An interleaved case

```json
{ "name": "an-append-after-the-first-round", "note": "…",
  "term": <term>, "root": "garden:1", "now": 100, "selection": {},
  "afterRound": 1,
  "append": { "expectedHead": "rounds-head-2", "nextHead": "rounds-head-3", "added": [ … ] },
  "expect": { "before": <expect, as in §5.4>, "after": <expect, as in §5.4> } }

{ "name": "a-purge-after-the-first-round", "note": "…",
  "term": <term>, "root": "garden:1", "now": 100, "selection": {},
  "afterRound": 1,
  "purge": ["g-features-c1-neg-neg"],
  "expect": { "before": <expect, as in §5.4>, "after": <expect, as in §5.4> } }
```

A case has exactly one of `append` and `purge`. `purge` holds corpus names, ascending by id.

`an-append-after-the-third-round` appends `late-c1-height-neg` after round 3. Round 3 finishes
`Leaf` at `cutting:1`, and the append strikes `c1-height` there. A wrapper that starts again but
keeps its evaluation memo shows the old `cutting:1` beside the new members: neither answer. The
cases that change the peer after round 1 cannot show it, because round 1 finishes no child.

The peer moves while a read is between two rounds. A reader needs a **hook** for this: a
callback it runs after each round's evaluation (§5.3 step 3.4) and before the next `scope` call,
also after the last round. The hook receives at least the round number (counted from 1 on each
snapshot), the attempt (1 for the first snapshot of a read; a wrapper that starts again counts
up) and the revision of the snapshot the round ran on.

For each case, on a newly loaded peer (§5.2), take a snapshot and start the read (mode 3). When
the hook reports round `afterRound`, change the peer once, then let the read go on. To change it,
apply `append` by the load rule (it MUST commit), or call `purge` with the ids that `purge`
names (every target MUST report `removed`). `after` is the read over the holdings after the
change. The read MUST end in one of two ways:

- it is refused with `snapshot-moved`; or
- it answers `expect.before` exactly (bytes, scope, members, rounds), at the revision of the
  snapshot it started on.

Anything else fails, in particular `expect.after` from a reader given one snapshot, and any
answer that is neither. The appended deltas are chosen so that a reader which goes on against the
later state shows some of them and not others, which is neither answer. The purged delta is one
that round 1 fetches. A store without read
transactions (the memory reference) refuses when a store call follows the append, and answers
`before` when `afterRound` is the last round. A store with read transactions answers `before`
every time.

A witness that offers a wrapper which opens the snapshot itself and starts again on
`snapshot-moved` (TypeScript: `StoreReactor.read`) runs each case through it too. It MUST answer
`before` at the first revision or `after` at a later revision, and never mix. `before` at a later
revision fails: it is what a wrapper answers when it starts again but keeps the old cache, and
the purge case shows it.

### 5.6 A refusal

```json
{ "name": "an-aliased-role", "term": <term>, "root": "garden:1", "now": 100,
  "expect": { "reason": "aliased" } }
```

The read is refused, and the refusal carries `reason`: the SPEC-17 §5 reason of the anchor
analysis (`aliased`, `reflection`, `const-group`, `result-sort`, `unknown-schema`). The reader
makes **no** store call. It does not fall back to another way of reading.

### 5.7 What is free

- The ids each round fetches. A store may return more than the scope (§1.4.1), so the vectors pin
  the anchors of each call and the exact members at the end, and not what came back in between.
- The order of `exclude`, and whether an empty `exclude` or an empty `pushdown` is sent or left
  out.
- The shape of the fetch cache, the hook, the report and the refusal in each witness.
- Whether the reader applies in memory a field the store reported applied. It changes nothing.
- How often a wrapper starts again after `snapshot-moved`. The TypeScript wrapper does so three
  times.

### 5.8 Rails each witness adds

The JSON cannot express these; each witness builds them over this fixture.

- **Wrong readers.** Each must fail at least one case:
  - A reader that sends the held ids as `pushdown.excludeIds` and not as `exclude`. Two things
    hide it. Against a store that leaves `excludeIds` to the host, it fails only if it also
    applies those ids as part of its residual selection, and so drops what it holds. Against a
    store that applies the field, it fails only if the store returns an unclosed extra (the
    `b1-late-note-neg-at-c2` shape of §5.4) and the read already holds it when a later round owes
    its negators. The rail needs both stores.
  - A reader that skips the residual selection. It fails under a switched-off field.
  - A reader that goes on in the middle of a read on a new snapshot, with its cache and its
    anchors. It fails an append case with an answer that is neither.
  - A wrapper that starts again on a new snapshot but keeps its old cache. Under appends alone it
    answers `after` exactly, because everything it kept is still held. It fails the purge case: it
    answers `before` at the later revision.
  - A reader that asks for every anchor in every round with the cache on. Its answers are right;
    it fails `expect.rounds`.
- **A sticky residual.** No vector pins it, because a memory profile is the same in every round.
  Each witness reads every case against a store double that leaves one field
  (`timestampAtMost`) to the host in the odd rounds only, and again in the even rounds only. The
  standard reader passes both parities. The control is a **reader** that never applies that field
  itself, over the same store double: it fails both parities. (A store that never applies the field
  is a different check: it is a switched-off profile of §5.4, where every round leaves the field
  to the host.) Both parities are needed, because a reader that forgets a residual can pass
  one of them. Measured in the TypeScript witness over the whole case set:
  - A reader that keeps only the **first** round's residual fails the even parity (round 1
    applied the field, so it never becomes residual; `signed-time-cuts-a-link-and-a-strike`
    fails) and **passes** the odd parity, where round 1 left it to the host.
  - A reader that keeps only the **current** round's residual (each round forgets what the round
    before it left to the host) fails **both** parities. In a round where the store applied the
    field, it stops trimming the members that an earlier round fetched past the cut, and the
    anchors it finds then stay in its scope. The even parity fails
    `signed-time-cuts-a-link-and-a-strike`; the odd parity fails that case and `every-field`.
  So the first-round reader is the one that needs both parities. Only a case whose selection has a
  time cut and that runs more than one round can show any of this.
- **Wrong evaluation memos.** Each must fail at least one case in mode 4 or 5, and a memo written
  by the rule of §5.4 must fail none:
  - A memo that stores every child, final or not. Round 1 evaluates the beds over the garden's
    scope alone and keeps the empty answer. It fails `the-whole-garden`.
  - A memo whose key leaves out the bindings. It fails `one-child-under-two-bindings`, and no
    other case.
  - A memo whose key does not tell two pinned references apart: for example, one that writes
    every pinned reference as the same key. It fails `one-child-under-two-pinned-schemas`. No
    other case names a schema by its hash.
  - A memo whose key leaves out the root. It fails `the-whole-garden`.
  - A memo kept across two reads: one store for every case of a run. It fails a case whose
    selection differs from an earlier case's (`signed-time-cuts-a-link-and-a-strike`).
  - A memo kept across the snapshots of one read, by a wrapper that starts again on
    `snapshot-moved`. It fails `an-append-after-the-third-round` (§5.5), and answers the round-1
    cases right.
- **What the memo saves.** Count through the memo hook, not by timing: one evaluation per child
  evaluated, a hit for each lookup that finds its key, and whether each evaluated child was
  stored. Against the same read with a memo that stores nothing: the memo makes strictly fewer
  child evaluations on a case of depth three; it stores each key at most once; and its evaluations
  equal the stored ones plus the ones that were not final. The TypeScript witness, counting one
  evaluation per stored-or-refused child, measures: `the-whole-garden` 159 without the memo and
  62 with it (18 keys, 18 stored, 44 not final, 42 hits); `one-child-under-two-bindings` 38 and 24
  (11 keys, 11 stored, 13 not final, 12 hits).
- **What the read reports about its memo** (SPEC-18 §4.12 reading 27). The answer of a read
  carries the number of child evaluations its memo held when it ended (TypeScript
  `StoreRead.memoStored`). The standard read of `the-whole-garden` (mode 5) reports 18; the same
  read with the memo off (mode 3) reports 0, and so does mode 2. No vector can see a read that
  ignores the memo switch, because the memo changes no answer; this count can.
- **The memo and a budget.** An evaluation with a budget and a memo never calls the memo; the
  same evaluation without the budget does.
- **The memo changes no report.** For every case, the round reports of modes 3 and 5, and of
  modes 2 and 4, are equal.
- **The hook.** For every case, the hook ran once per round, also after the last round, and its
  reports equal the read's own round reports. A read that a wrapper started again reports each
  attempt, and the reports of two attempts differ in `attempt` and `revision`.
- **Refusals.** A store double that refuses one `scope` call with `snapshot-released`, and one
  with `capability-absent`. The wrapper (`read` and `fetch`) passes the refusal up after one
  attempt and releases the snapshot.
- **A store that lies about `applied`.** A double that drops `timestampAtMost` and reports it
  applied. The read trusts `applied` (SPEC-18 §4.12 reading 18), so its answer is wrong. The rail
  shows that this trust is a stated assumption: the store vectors, not the read, catch the lie.
- **The fetch cache.** The ownership tests of §7 for the cache and for each source it hands out:
  a driver that writes into its byte array after `scope` returns, a caller that changes a
  returned delta, payload, arrival record or index list, bytes that are not the byte array type.
  A member with no arrival record, and one whose arrival names another id, is refused, and a
  refused call adds nothing. Index rules: a delta with two pointers at one entity is listed
  once, and a pointer at a delta whose role is not `negates` makes no negator. No vector reaches
  these: the reader computes members as a set, and a correct store never returns the second
  shape where it could matter.
- **Cost.** With a snapshot wrapper that records `{op, keyCount, excludeCount}` for every call:
  the same read beside 0 and beside at least 4000 unrelated deltas makes the same calls, and the
  memory store's meter moves by the same amounts with no scan; each round is one `scope` call
  whose `keyCount` is that round's anchor count; no other operation is called.

## 6. What the vectors do not cover

- The journal, stored views, derived indexes, value-lookup and derived-index anchors, digests.
  Freshness reads entity anchors only (§9).
  Slice 1 has none of them. The change feed is in §3.9; its cost is a rail of each witness
  (§3.9.9), and the store options for retention and pages are each witness's own.
- An unknown anchor kind, a missing posture, and non-finite numbers (§1.2, §1.4.1). JSON or a
  typed witness cannot express them; each witness tests what its language can express.
- **Ownership** (§1, "A store owns what it holds", "A store never converts"). A conformance run
  hands a store values and compares what comes back; it never changes a value afterwards and
  never passes a value of the wrong type. The one exception is the change feed: the runner
  changes every page `changes` returned and asks again (§3.9.5, check 14). Elsewhere, a store
  that keeps the caller's objects, returns its own, or shares a payload's memory passes every
  vector. Ownership is an obligation of each
  witness and of each store, with its own tests (§7).
- A purge on a store of class `none`. The scripts that purge are skipped for such a store, so no
  shared step shows that it refuses. Each witness tests that refusal for its own stores (§7,
  test 8).
- Proof of physical absence. The memory reference store is `unprovable`. A `proven` store adds
  its own adapter rails for its surfaces (SPEC-18 §8).
- Cost. A JSON file cannot measure work. Each witness has its own cost rails (SPEC-18 §8):
  - **Core operations.** A rail asserts that no core operation walks a whole set. A memory store
    may count its own index work for this, as the reference does.
  - **Building `scopeSource`.** A rail times the build from outside, with a monotonic clock. It
    builds the source in four shapes, each at N and at 8N:
    1. N members, each a fact about one shared entity;
    2. N members, each a negation of one shared delta;
    3. one member with N pointers, each to its own entity;
    4. N appearances of four ids: four members in turn, so every appearance after the fourth is
       a repeat.

    For each shape, N is the smallest power of two from 256 whose build takes 50 ms or more. A
    witness may cap N where 8N members would not fit in memory; the rail then names the cap.
    The build at N is the fastest of five builds. The build at 8N is the fastest of three; the
    rail may stop at the first build under the bound, because the fastest is under the bound
    exactly when one build is. The ratio of the two must stay below 24: linear work gives about
    8, and quadratic work about 64. A quadratic build reaches 50 ms at a small N, so it fails
    rather than hangs. A witness may measure a slow shape again, as in §3.9.9.

    This is a coarse scaling check, not a count. It catches a copy or a search of a list per
    insert: of a bucket (shapes 1 and 2), of one member's keys (shape 3), of what earlier
    appearances left (shape 4). It is coarse in one direction. A stall must slow all three
    builds at 8N to fail correct code, but a stall during every build at N lowers the ratio, so
    a loaded machine can let a quadratic build pass. It cannot see a quadratic term too small
    to show at that N. A count kept by the code under test does not serve, because that code
    can do work it does not count. Each witness measures each shape red once, against a build
    that does that shape's quadratic work: a list of a member's entity keys searched before
    each insert (shape 3), and a list of earlier appearances copied on each repeat (shape 4).
- `store-closed`, `openStore` and URL schemes. These are host API, tested per witness. One rule
  binds every witness that opens by URL: the options of `openStore` are absent (none) or a plain
  object, and its `requires` is absent (none) or a list of strings. A dynamically typed witness
  refuses anything else with `invalid-request` and one fixed message that quotes nothing the
  caller gave, reads the options once, and hands the store's factory its own copy.
- The runner. The vectors judge a store through a runner, and nothing in the vectors judges the
  runner (§8).

## 7. What a store tests for itself: ownership

A store that passes the vectors has not shown that it owns what it holds. Whoever writes a store,
a witness or a consumer, tests these for that store. Each test changes a value the test still
holds and then reads the store again; the store's answers MUST NOT change.

1. **After append.** Append a signed delta with a bytes payload, to two peers. Then change every
   part of what was appended: each claims field, a pointer's role and target, the list of
   pointers, the payload's bytes, the signature, the id, each field of the arrival record. Every
   read of both peers answers as before.
2. **After a read.** Change every part of what `get`, `arrivals`, `scope` and the exporter
   returned, the payload's bytes and the memory behind them included. Every later read, of this
   peer and of every other peer that holds the id, answers as before. Two reads of one id share
   no memory with each other.
3. **Payload memory.** For every byte container the language has, append a payload held in it,
   then write to the caller's memory. The store's bytes do not change. In TypeScript the
   containers are a plain `Uint8Array`, a Node `Buffer`, a subclass, a view of part of a larger
   buffer, and a view over shared memory; in Rust the type system gives this for owned vectors,
   and a store that takes shared or borrowed bytes tests it.
4. **No conversion** (a dynamically typed witness). For each position of an entry, pass a value
   of another type that a lenient store could convert: a buffer or a list of numbers for a
   payload, a numeric string for a number, a string object for a string, an object with indexes
   for a list. Use the id the converted form would have. The store refuses and holds nothing.
5. **One read of each field** (a witness whose objects can answer differently on each read). For
   every field the store keeps or acts on, pass a value that is honest on its first read and
   wrong on every later read. The fields are: each field of the claims; inside the claims, the
   list of pointers, each pointer, a pointer's role and target, a target's kind, an entity's id
   and context, a delta reference and its id and context, a primitive value, a mime type and the
   payload's bytes; the signature; the delta's id; each of the five fields of the arrival
   record; and the fields of a request (the ids of `get`, `arrivals`, `negators` and `purge`,
   the entities of `targets`, and the anchors, the bounds, `excludeIds` and `exclude` of
   `scope`). The store may admit or refuse. If it admits, what it keeps and answers is a value
   it checked: it MUST NOT hold the id over claims that do not recompute, keep a signature or
   an arrival record that its checks would refuse, or answer a request other than the one it
   checked. A store that reads each field once admits every such entry and keeps the honest
   values.
6. **The profile.** Change the profile a caller reads, or replace it. The posture gate and the
   applied pushdown fields do not change. Nothing the store decides by is reachable from a
   handle.
7. **`scopeSource`.** It has one input, the list of members, and its answers. Build a source
   from a list of members, then repeat tests 1 to 5 against it: change the members and the list
   after the build, change what `get` and `arrival` return, and pass members whose fields answer
   differently on each read. Its answers (`get`, `arrival`, `targets`, `negators`, `ids`) MUST
   NOT change, and it MUST NOT file a member under an id its claims do not recompute to. Test 3
   applies to the payload of a member. Tests that need two peers do not apply.
8. **A store of class `none`.** Every `purge` refuses `capability-absent`, an empty purge too,
   and changes nothing: the holdings, the head and the revision stay. A witness that has no store
   of class `none` has nothing to test here.
9. **`changes`** (a witness whose values can be changed after they are returned). Read a page.
   Change its list of records, each record, and each record's `added` and `removed` lists. Read
   the same range again: the answer is the one from before. The runner does this on every page
   (§3.9.5, check 14), so a store that hands out its own lists fails the vectors too.

## 8. What a witness tests for itself: the runner

A runner that stops checking a rule still passes the memory store, so the vectors cannot hold a
runner to this page. Each witness keeps a table of wrong stores, one per rule of §3 and §4. A
wrong store is the memory store behind a thin wrapper that breaks that one rule and nothing a
script meets before it. For each, the conformance run MUST fail, in the expected document, with
the message of that rule. Asserting the message matters: a script stops at its first failing
step, and many wrong answers are caught by a later, unrelated check when the rule's own check is
gone.

The table covers at least:

- **Refusals:** a code outside the step's list, for `createPeer`, `openPeer`, `append`, a query
  and `export`; an answer where a refusal is expected; a refusal where an answer is expected; on
  a moved snapshot, a refusal that is not `snapshot-moved`.
- **Peers:** a created or opened handle with another posture; a created handle with another
  erasure class than the profile; `unlessStoreErasure` in both directions.
- **Append:** each answer that is not the expected one, `uncertain` included; the added ids, and
  their order; the result's revision; a refused append or a `conflict` that moves the revision,
  up and down; `revisionAdvanced` in both directions.
- **Purge:** outcomes (not ids only), their order, a repeated id; the report's revision;
  `revisionAdvanced` in both directions; the boundary text, exactly; each claim that is not the
  expected one; `proven` with no surface and with a surface that is not `absent`; a surface state
  outside the three.
- **The bookkeeping:** the first entry of a batch with an id is the one held; a purge forgets
  the id, so an id appended again is held under its new arrival record. Both outcomes that end
  a holding: a store that keeps the old record after `removed`, and one that keeps it after
  `held-by-other-peer`. And a store that keeps the record while a debt is owed and forgets it
  when an append clears the debt, but not when a later purge settles it.
- **Point reads:** `head`, and a new peer's head that is the empty string instead of null;
  `count`; ids and their order for `get`, `arrivals`, `targets`, `negators`; a returned delta's
  signature and claims; each of the four fields of an arrival record.
- **Scope members:** order, a repeat, claims, the arrival record's id and fields, the signature,
  a member the peer does not hold.
- **Scope bounds:** `applied` ⊆ requested; the lower and the upper bound in a script and in a
  scope case; the trim comparison. In a scope case, the lower bound twice: a store that leaves
  out the first id of the bound, and one that leaves out a later id.
- **Reference rules:** the applied fields, the exact ids in a script and in a scope case, the
  surfaces. For each, the same wrong answer under another `formatVersion` conforms. The exact
  ids in a script also for a step with no `pushdown`: a store that ignores `exclude` only when
  no pushdown is asked.
- **Export:** ids, their order, the count of deltas in both directions (fewer deltas than ids,
  and more), a delta's appearance; the stored listing and the peer listing.
- **Requirements:** each one skips exactly its scripts and reports them; each script gets a new
  store.
- **Stores that must pass.** Right answers the runner must accept: stores whose revisions are the
  reference store's times 2, times 3 with pages of one record, times 2 keeping two records, and
  times 3 keeping two records with pages of one record. Each answers every rule of §3.9.1,
  scaled: `changes(from, to)` asks the reference for `floor(from / k)` to `floor(to / k)`, and a
  complete page says `through` = the clamped `to`. It refuses `to < from` itself, and answers
  `resync-required` itself for a `from` above k times the reference's revision. Each passes
  every vector. A fifth right store answers pages of at most 1, then 2, then 1, then 2 records,
  call by call: the same request gets another prefix (§3.9.5, check 14).
- **More feed rows** (second review): revisions times 3 and times 2, two records kept, that
  answer `ok` just below the floor by reading on past the newest dropped record (§3.9.4, item
  2); a wrong `current` on the call below the floor only, in a script with no `changes` step;
  an extra key only on the answer asked again after a change (§3.9.5, check 14); an `ahead`
  that is negative and one that is fractional (documents); a `changes` step that expects
  `resync-required` where `ok` is right (a document; it reaches
  `changes answered ok from <from>, and the step expects resync-required`).
- **Rows in one witness only.** Each witness names, in its rule-table file, the rows it cannot
  build and why:
  - Rust has no row for exact keys (§3.9.3), for a page that is neither `ok` nor
    `resync-required` (§3.9.5, check 3), or for the store that hands out its live records or
    live id lists (check 14). Its `ChangeRecord` and `ChangePage` types have exactly the
    contract's fields and two statuses, and a returned page is owned by the caller, so no
    store can reach those rules. Rust's row `AnswersTwoWays` (a store that answers the asking
    again of check 14 differently) stands in for the live rows and holds the re-ask to its
    message. The shape check on the asking again (TypeScript row "an extra key only on the
    answer asked again") is type-unreachable in Rust for the same reason.
  - TypeScript has no `AnswersTwoWays` row. Its rows for live records and live id lists reach
    the same message, `changes answered differently after the caller changed what it
    returned`, through the change the runner makes.
- **The change feed** (§3.9), one wrong store per message of §3.9.3 to §3.9.6, at least:
  no record for a head-only commit; no record for a commit that adds; two records for one
  commit; a record for a step that did not advance; a record with another head; one that adds
  nothing; a settled debt in `removed`; ids out of order inside a record; a commit check that is
  not `ok`; `changes` that refuses; a silent gap (records dropped, `ok` answered); a resync
  inside the window; a resync on a later page; a resync with another `current`; a page that is
  neither `ok` nor `resync-required`; an overstated page (`through` past what the records cover);
  records out of order; a record outside the range; a `through` past the range; no progress on a
  range with records; two peers mixed in one feed; a record changed after it was written; a
  record that differs from its commit the first time it is seen; and a store that declares
  `{revisions: 2}` and answers `ok` below its floor; a record with an extra key that carries
  bytes; an `ok` page and a `resync-required` answer with an extra key; a store that hands out
  the same record objects on every answer; one that hands out the same id lists; a store whose
  revisions are twice the reference's, with pages of one record, whose partial page says
  `through = last + 1` (check 12 of §3.9.5); a store whose revisions are three times the
  reference's, keeping two records, that answers `resync-required` for a `from` between the
  newest dropped and the oldest kept revision (the floor probe of §3.9.4); a store whose
  revisions are three times the reference's, keeping two records, that reads on past the newest
  dropped record and answers `ok` only where `from % 3` is 1 (the row "ok two below the floor and
  right one below it": wrong at F − 2, right at F − 1, so item 2 of §3.9.4 must probe every
  integer between the revision before the newest dropped record and F); the same with revisions
  1000 apart, wrong wherever `from % k` is `k − 2` below the floor, which between the revision
  before the newest dropped record and F is F − 2 alone (among the last eight points of the
  bounded probe). A store whose
  revisions are 1000 apart, keeping two records, must pass. Most break the feed
  only when two or more records are pending, so the check of each commit, a range of one, still passes and the rule's
  own message is the one that fails. Two messages are shared by the check after every step and
  the `changes` step ("every record after … is retained", "below the retention floor"). Each
  needs two rows: one with a script that has no `changes` step, and one with a store that is
  wrong only when a `to` is given, which the check after every step never gives.
- **Documents:** an unknown `format`; a corpus id that does not recompute and is not `forged`; a
  purge `claim` with a key other than `unprovable` and `proven`; an unknown script requirement;
  a script `requires` that is `null`; a revision name that is unknown, of another peer, or given
  twice; a `mark` before its peer; `changes` expectations that are wrong; a `changes` step on a
  store without a feed; a profile whose `changeRetention` is malformed, among them
  `{revisions: 2^53}`, which is an integer and not a safe one. A defect of one
  script's `requires` is a failure of that script, reported by name with the run's other
  failures, and the run closes that script's store.

A rule a wrapped store cannot reach is listed by name in the test file, with the reason. Then the
table itself is checked once: for each check of the runner, remove it and see the table go red.

## 9. `freshness.json`

This file pins the freshness check of SPEC-18 §4.6: a **capture** of what one anchored read
depended on, the pure function **`touching`**, and **`checkFresh`** over a peer's change feed. A
run tests a store and a witness's three freshness functions together.

Every expectation comes from the list-scanning model of `scripts.json` (§3.3, §3.4, §3.9.2).
A capture's members are S(anchors) over the model's holdings. Its window (`since`, `expiresAt`)
is a scan of the selected scope. A check's touch is a plain scan of the model's records. The generator then proves
each check without a selection **exact** by brute force: it recomputes S(anchors) over the
holdings at the check, with arrival records, and requires that there is no touch exactly when
that set equals the members, every member keeps its arrival record, and no member left and came
back. For a check with a selection it proves soundness: when the selected scope changed, there is
a touch. A case that breaks either fails generation.

### 9.1 The document

```json
{
  "format": "rhizomatic-store-freshness/1", "note": "…",
  "reference": { "formatVersion": "rhizomatic.store.memory/1" },
  "peers": { "A": "ed25519:c3c3…", "B": "ed25519:a1a1…" },
  "deltas": [ { "name": "a-name", "id": "1e20…", "claims": { … } } ],
  "cases": [
    { "name": "an-added-negator-of-a-member", "note": "…", "spec": "SPEC-18 §4.6",
      "requires": ["changes"],
      "store": { "changeRetention": { "revisions": 1 } },
      "steps": [ <steps> ] } ],
  "touching": [ <touching case> ]
}
```

- `format`: refuse any other value, with `unknown store freshness format`. That is one failure of
  the run, named `freshness`, in its failure report, not a run that throws or refuses to start.
  `reference`, `peers` and `deltas` are the common header of §2. No entry is signed or forged.
- `cases`: run each on a **new** store. `requires` is a list of requirement names, as in §3; every
  case lists `changes`. Skip a case whose requirement fails, and report it skipped.
- `store` (optional): build the case's store with this change retention (`unbounded` or
  `{revisions: n}`). It replaces the retention of the run (§9.4). The runner checks the field
  first: another field, or a value of another shape, is a document defect that fails the case
  (§10.1 has the messages). A factory that cannot build such a store skips the case and reports
  it skipped, with the requirement `store`. Any other failure of the factory fails that case
  only: `the factory did not open a store: <error>`.
- `steps`: the steps of §3 (`createPeer`, `append`, `purge`, `mark` and the rest), run with the
  same checks, bookkeeping, revision names and feed model, and with the feed check after every
  step (§3.9.4). Two more ops: `capture` (§9.2) and `check` (§9.3). The feed check runs after
  these two as well.
- `touching`: cases of `touching` alone (§9.5).

### 9.2 `capture`

```json
{ "op": "capture", "peer": "A", "as": "c",
  "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
  "selection": { "timestampAtMost": 50 }, "now": 100,
  "expect": { "revision": "A.2",
              "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
              "members": ["a-height", "a-name", "a-height-neg", "a-future", "a-late"],
              "since": 20, "expiresAt": 120 } }
```

`peer` is a handle name (§3.2). `anchors` are as a read names them: in any order, perhaps
twice; the capture sorts them and drops repeats. `selection` (optional) is the read's whole selection in pushdown
form, with corpus names in `excludeIds`; absent means none. `now` is the read's evaluation time.

The runner builds captures only through the witness's capture function or its checking
constructor (`parseCapture`), and hands `checkFresh` and `touching` only those. A witness's
`touching` and `checkFresh` refuse `invalid-request` any other object (SPEC-18 §4.6); a typed
witness whose capture type has private fields and only these two constructors meets this by
construction, as the Rust witness does. The maker builds a capture from a live snapshot; it is
not a way to reload a stored capture, which comes back only through the parser.

Take a new snapshot of the peer. Build a capture on it with the witness's own capture function,
for these anchors, this selection and this `now` (TypeScript: `captureScope(snapshot, entities,
now, {pushdown})`). Release the snapshot. Then check, in this order:

0. The capture is well formed by the witness's checking constructor (TypeScript:
   `parseCapture`, SPEC-18 §4.6, except that a history local to the process is allowed here):
   exactly the six fields, a non-empty history, an integer revision, both lists strictly
   ascending by UTF-8 bytes, `since < expiresAt` when both are numbers. Else
   `the capture is malformed: <the constructor's reason>`; the reasons start `capture: ` (for
   example `capture: anchors is not strictly ascending by UTF-8 bytes`). A typed witness whose
   capture exists only once a constructor checked it cannot return a malformed one. Its maker
   refuses inside the capture function instead, and the runner reports that refusal with the
   same words. Then its history is the snapshot's, else
   `the capture's history is not its snapshot's`.
1. The capture's revision is the snapshot's revision, and it is the revision `expect.revision`
   names. Else `the capture is of revision <r>, expected <R>`.
2. Its anchors equal `expect.anchors`, in order: ascending by the UTF-8 bytes of the entity,
   unique. Else
   `the capture's anchors are [<kind>:<entity> …], expected [<kind>:<entity> …]`.
3. Its members equal the ids of `expect.members`, in order. The members are the **raw** scope,
   S(anchors over H) with no selection: a capture never takes them from a pushed-down fetch.
   Else `the capture's members are [<ids>], expected [<ids>]` (each id cut to 12 characters).
4. Its `since` equals `expect.since`, else `the capture's since is <x>, expected <y>`; then its
   `expiresAt` equals `expect.expiresAt`, else `the capture expires at <x>, expected <y>` (each
   a number, or `null`). Over the deltas of the read's exact scope under its selection, negators
   included (not the raw scope, and not what the store returned), `since` is the greatest
   `validFrom` or `validUntil` at or before `now`, and `expiresAt` the least strictly after it.

Keep the capture under the name `as`, with the peer its handle belongs to. A name given twice is
a defect: `the vector names capture <as> twice`.

### 9.3 `check`

```json
{ "op": "check", "peer": "A", "capture": "c", "now": 120, "exact": true,
  "expect": { "revision": "A.3",
              "verdict": { "status": "stale",
                           "touch": { "revision": "A.3", "delta": "a-name-neg", "reason": "negates-member" } },
              "touching": { "revision": "A.3", "delta": "a-name-neg", "reason": "negates-member" } } }
```

- `now`: passed to `checkFresh`. It is required; a check without it is a document defect,
  `the vector's check has no now`.
- `anotherPeer` (optional, `true`): the handle belongs to another peer than the capture's, on
  purpose. That peer has another history, so the expected verdict is `resync-required`, the
  retention floor is not consulted, and check 6 (`touching` alone) is not run. Without this key,
  a check on another peer is a document defect; with it, a check on the same peer is one:
  `the vector says capture <name> is checked on another peer, and it is not`.
- `exact`: true when the generator proved the verdict exact; false when the capture has a
  selection and the verdict is only sound. A false `stale` is then possible and expected (the
  case `a-selection-rejects-the-toucher`). The runner does not read this field.
- `expect.revision`: the peer's revision when the check runs. It must be the model's current
  revision of that peer; else the document is wrong:
  `the vector checks at <name>, and the peer is at <r>`.
- `expect.verdict`: `{"status": "current"}`, `{"status": "stale", "touch": <touch>}`,
  `{"status": "not-yet", "since": <number>}`, `{"status": "expired", "expiresAt": <number>}` or
  `{"status": "resync-required"}`. The order is `resync-required`, `stale`, then the window
  (`not-yet` when `now < since`, `expired` when `now ≥ expiresAt`), else `current`. A touch is
  `{revision, delta, reason}`: a revision name, a corpus name, and `removed-member`,
  `targets-anchor` or `negates-member`.
- `expect.touching`: what `touching` answers over every record since the capture, kept or not
  (a touch, or null).

Document defects: `the vector uses capture <name> before taking it`, and
`the vector checks capture <name> on another peer` (the handle belongs to another peer). A check
on a store with no feed: `a check step on a store that serves no feed`.

**The expected verdict.** Let F be the peer's retention floor in the runner's model (§3.9.2). When
the check is not on another peer and the capture's revision is below F, the expected verdict is `{"status": "resync-required"}`,
whatever the document says: a document is written for a feed that keeps every record.
Otherwise it is `expect.verdict`.

**The call.** Wrap the peer handle so that every call through it, and through every snapshot it
returns, is logged with its arguments and its answer (for `read`, the snapshot's revision and
history). Log each call when it is made, also a call that then refuses. Call
`checkFresh(wrapped, capture, now)`.
It must answer. A store refusal that passes up out of it fails with
`checkFresh refused with <code>`, followed by the refusal's message. A store fault (SPEC-18 §4.13
reading 73) fails with `the store broke <rule>: `, followed by the fault's message; `<rule>` is
`no-progress`, `past-the-bound`, `mismatched-answers` or `unasked-ids`. Then check, in this order:

1. The status equals the expected status. Else, below the floor,
   `checkFresh answered <s> for a capture below the retention floor F`, and otherwise
   `checkFresh answered <s>, expected <e>`.
2. `stale`: the touch equals the expected touch: revision (the named revision's integer), id and
   reason. Else `checkFresh reports the touch <r> <id> <reason>, expected <r> <id> <reason>`
   (each id cut to 12 characters).
3. `not-yet`: `since` equals the expected value, else
   `checkFresh reports not-yet since <x>, expected <y>`. `expired`: `expiresAt` equals the
   expected value, else `checkFresh reports expiry at <x>, expected <y>`.
4. `resync-required`: `current` is the peer's current revision. Else
   `checkFresh reports resync-required with current <c>, not the peer's revision <r>`.
5. **The calls.** Write each call as text: `read`; `changes(<from>, <to>)`, with `none` for an
   absent `to`; `get [<ids>]`, each id cut to 12 characters, joined by spaces; `release`; and
   any other operation by its name (`targets`, `negators`, `scope`, `arrivals`, `append`,
   `purge`). Walk the log against the contract:
   - The first call is `read`. Let r′ be the revision of the snapshot it returned and c the
     capture's revision.
   - When the snapshot's history is not the capture's, go to the last item: no feed call.
   - When r′ > c: set `at = c`. The next call is `changes(at, r′)`. When it refused or answered
     `resync-required`, stop. Otherwise, when its records name an added id, the next call is
     `get` of every id in some record's `added`, distinct, ascending. When the expected verdict
     is `stale`, stop when a record of the page has the expected touch's revision. Stop when
     `through ≥ r′` or `through ≤ at`.
     Otherwise set `at = through` and repeat.
   - The next call is `release`, and it is the last.

   A call that differs from the one the walk asks for fails with
   `checkFresh made the call <actual> where the contract asks for <expected>`. A missing call
   fails with `checkFresh made no call where the contract asks for <expected>`. A call after the
   last fails with `checkFresh made the call <actual> after its last call`.
6. **`touching` alone.** Take the runner's model records of the peer (§3.9.2) with
   `c < revision ≤ r′`, kept by the store or not, as copies. Take, for every id in some record's
   `added` that the bookkeeping (§3.3) says the peer holds now, the appearance it holds. Call
   `touching(capture, records, those deltas by id)`. The answer equals `expect.touching`. Else
   `touching answered <touch or none>, expected <touch or none>`, a touch written as in check 2.

The runner never commits while a check runs, so a `checkFresh` that starts again on a new
snapshot after `snapshot-moved` (SPEC-18 §4.13 reading 35) is never seen here.

**Messages.** As in §3.9, the fixed words of each message of §9.2 and §9.3 are normative. Every
failure message carries its fixed words; a witness MAY put a locator of the step before them
(the TypeScript runner writes `step <n> (<op>): `). This holds for §10 too. How a value inside a
message is rendered is each witness's own: an id cut or whole, a number, a list of anchors. Each
witness's table of wrong readers pins its own rendering.

### 9.5 A `touching` case

```json
{ "name": "removed-before-added-in-one-record", "note": "…",
  "capture": { "revision": 4, "anchors": [ { "kind": "entity", "entity": "plant:a" } ],
               "members": ["a-height", "a-name", "a-height-neg"] },
  "records": [ { "revision": 5, "head": null, "added": ["a-name-neg"], "removed": ["a-name"] } ],
  "held": ["a-name-neg"],
  "expect": { "touch": { "revision": 5, "delta": "a-name", "reason": "removed-member" } } }
```

No store wrote these records. Revisions are integers. Every name list is in ascending id order.
Build a capture through the checking constructor with history `"touching"`, this revision, these
anchors, the ids of `members`, and `since` and `expiresAt` null. The lists are in UTF-8 order, so
it accepts them.
Map `records` to change records with ids. Map `held` to the corpus deltas by id: the added ids the
peer still holds at the end. Call `touching`. The answer equals `expect.touch` (`revision` an
integer), else `touching answered <touch or none>, expected <touch or none>`.

These cases pin what a store's records cannot reach: `removed` before `added` within one record
(no store yet writes a record with both), the reason of a delta that both points at an anchor and
negates a member (`targets-anchor`), and an added id no longer held.

### 9.6 What the cases hold

- No change, at the capture's own revision; a head-only commit; unrelated appends.
- An added delta that points at an anchor; an added negator of a member; an added negator of a
  negator that is a member; an added negator of a non-member (current); an annotation of a
  member under another role (current).
- A purge of a member; a purge of a non-member (current); a member purged and added again (stale
  at the purge); a would-be toucher added and purged within the range (current).
- Another peer that holds the same bytes and adds deltas at the anchor (current).
- Several touches: an unrelated append, a purge of a member, then two touchers; the purge is
  first. Two touchers in one record; the lower id is first.
- Two anchors. A touch only through a dynamic anchor (an expanded child), beside a capture of the
  root alone that stays current.
- A store that keeps one record: `resync-required`.
- The window (`the-window`): a capture at `now` 100 whose window is [100, 120), with a boundary
  outside the scope that does not count; checks at 99 (`not-yet`), 100 (current, at `since`),
  119 (current, just below `expiresAt`), 120 (`expired`), at 200 (`expired`), and at 200 and at

- One fact valid from `now` (`a-fact-that-starts-at-now`): window [100, open); a check at 99 is
  `not-yet`.
- A negator of a member valid from 25 until 130 sets the window alone
  (`a-negator-sets-the-window`): checks at 24, 25, 129 and 130.
- A chain of four (`a-chain-of-four`): a member two negations deep, and an added third negation
  of it. A raw scope that stops after one negation layer misses the member. The case captures

  witness compute the raw scope from ids alone.
- A capture checked on another peer with a higher revision (`a-capture-checked-on-another-peer`):

- Selections: `timestampAtMost` 50 with a raw member it rejects, whose boundary at 105 does not
  count; a toucher it rejects (stale, sound, not exact); a purge of that raw member; a negator

  operand's (`a-selection-excludes-members`). `arrivalAtMost` 4 dropping a member that arrived
  fifth, with a window inside the operand's (`a-selection-by-arrival`).

## 10. `follow.json`

This file pins the feed cursor of SPEC-18 §4.6, "Following the feed": `positionOf`, a cursor that
`follow` makes, and its `pull`. A run tests a store and a witness's follower together.

Every expectation comes from the list-scanning model of `scripts.json` (§3.3, §3.4, §3.9.2). A
pull's records are a scan of the model's feed; its delivered ids are the added ids the model
holds. The generator then proves the follower's guarantee by brute force: a mirror that starts
from the holdings at the follow and applies each pull by the rule of SPEC-18 §4.6 equals the
holdings, with their arrival records, at the end of every pull step that reaches the peer's
revision; after a single pull short of it, it equals the holdings for every id no later record
names. It does this with whole pages and with pages of one, two and three records, or, in a case
that pins its page size, with that size. A case that breaks it fails generation.

### 10.1 The document

```json
{
  "format": "rhizomatic-store-follow/1", "note": "…",
  "reference": { "formatVersion": "rhizomatic.store.memory/1" },
  "peers": { "A": "ed25519:c3c3…", "B": "ed25519:a1a1…" },
  "deltas": [ { "name": "a-name", "id": "1e20…", "claims": { … } } ],
  "cases": [
    { "name": "pages-of-one", "note": "…", "spec": "SPEC-18 §4.6",
      "requires": ["changes"], "store": { "changePageSize": 1 },
      "steps": [ <steps> ] } ]
}
```

- `format`: refuse any other value, with `unknown store follow format`. That is one failure of the
  run, named `follow`, in its failure report, not a run that throws or refuses to start.
  `reference`, `peers` and `deltas` are the common header of §2.
- `cases`: run each on a **new** store. `requires` is as in §3; every case lists `changes`. Skip
  a case whose requirement fails, and report it skipped.
- `store` (optional): `changeRetention` (`unbounded` or `{revisions: n}`) and `changePageSize`
  (n ≥ 1). Each field present replaces the run's (§10.4). A case with a single pull (`once`,
  §10.3) sets both, so every run reads the same pages. The runner checks `store` before it builds
  anything; each defect fails the case: `the case's store is not an object`,
  `` the case's store sets an unknown field `<key>` ``,
  `the case's changeRetention is not unbounded or {revisions: n}`,
  `the case's changePageSize is not a whole number of 1 or more`. A factory that cannot build such
  a store skips the case and reports it skipped, with the requirement `store` (TypeScript: the
  factory answers `undefined`; Rust: it refuses `capability-absent`). Any other failure of the
  factory fails that case only, and the other cases run:
  `the factory did not open a store: <error>`.
- `steps`: the steps of §3, with the same checks, bookkeeping, revision names and feed model, and
  the feed check after every step (§3.9.4). Two more ops: `follow` (§10.2) and `pull` (§10.3).
  The feed check runs after these too.

### 10.2 `follow`

```json
{ "op": "follow", "peer": "A", "as": "f", "expect": { "revision": "A.1" } }
{ "op": "follow", "peer": "A", "as": "f", "ahead": 2, "expect": { "revision": "A.1" } }
{ "op": "follow", "peer": "A", "as": "f", "historyOf": "B", "expect": { "revision": "A.1" } }
```

`peer` is a handle name (§3.2). Take a new snapshot of it, call the witness's `positionOf` on it,
and release it. Then check, in this order:

1. The position's history is the snapshot's, else `the position's history is not its snapshot's`.
2. Its revision is the snapshot's, and it is the revision `expect.revision` names, else
   `the position is of revision <r>, expected <R>`.

Then build the position to follow from: the history is the position's, or, with `historyOf` (a
handle name), the history of that handle's peer; the revision is the position's plus `ahead`
(absent: 0). An `ahead` that is not an integer of 0 or more is a document defect,
`the vector's ahead is not a whole number`. Call the witness's `follow` with a **logged** handle
of the peer (§10.3, "The calls") and that position. A refusal fails with
`follow refused with <code>`, followed by its message. Check:

3. The new cursor's position is the position given, history and revision, else
   `a new cursor stands at <r>, not at the position it was given`.
4. Following made no store call, else `following made the call <call>; it makes no store call`.

Keep the follower under the name `as`, with the peer the handle belongs to, its logged handle and
a **mirror**: a copy of the bookkeeping of §3.3 for that peer (id → delta and arrival record).
The mirror is what a follower that read the peer's whole state on the snapshot holds. A name
given twice is a defect: `the vector names follower <as> twice`.

### 10.3 `pull`

```json
{ "op": "pull", "follower": "f",
  "expect": { "status": "ok", "position": "A.4", "records": ["A.2", "A.3", "A.4"],
              "delivered": ["b-name"], "absent": [], "pulls": 3 } }
{ "op": "pull", "follower": "f", "expect": { "status": "resync-required", "current": "A.3" } }
{ "op": "pull", "follower": "f", "once": true,
  "expect": { "status": "ok", "position": "A.1", "records": ["A.1"], "delivered": ["b-name"], "absent": [] } }
```

**`once`** (optional, `true`): the step makes **exactly one pull**, and `position` names where
its one page ends, which may be short of the peer's revision. It appears only in a case whose
`store` sets both `changePageSize` and `changeRetention`. Commits between single pulls then show
what a catch-up of one snapshot cannot: each pull delivers the bytes held at its own snapshot.

A `pull` step **pulls until the follower stands at the peer's current revision**, or until a pull
answers `resync-required`. With whole pages that is one pull. With pages of one it is one pull per
record. So the expectations do not depend on the page size: `records` lists the revisions of
every record the step's pulls read, in order; `delivered` the ids they delivered, distinct,
ascending by id; `absent` the added ids with no bytes, because the peer no longer holds them
(the runner does not read `absent`); `pulls` (only in a case whose `store` sets
`changePageSize`) how many pulls the step takes. A pull step on an unknown follower is a defect:
`the vector uses follower <f> before following`. On a store with no feed:
`a pull step on a store that serves no feed`. The defect of the document comes first: an unknown
follower on a store with no feed fails with the first message.

**The expected status.** In this order:

- The follower's cursor answered `resync-required` before, in this run: every pull answers it
  again, with the same `current`, whatever the document says. (A store that keeps fewer records
  than the document's may have stopped this cursor in an earlier step.)
- The document says `resync-required`: `current` names the peer's current revision, else the
  document is wrong, `the vector expects current <name>, and the peer is at <r>`.
- The document says `ok`: without `once`, `position` names the peer's current revision, else
  `the vector pulls to <name>, and the peer is at <r>`. When the cursor's position has the peer's
  history and lies below the retention floor F of the runner's model (§3.9.2), the expected status
  is `resync-required` with the peer's current revision, whatever the document says.

**Each pull.** Before each pull, start a new call log. Let `before` be the cursor's position and
`end` the model's current revision. Let the bound be one more than the number of model records
after `before`; a step that takes more pulls fails, `the follower took more than <n> pulls to
reach <end>`. Call `pull()`. A store refusal that passes up fails with `pull refused with <code>`,
followed by its message. A store fault fails with `the store broke <rule>: `, followed by the
fault's message (as in §9.3). Any other error fails the case with its own message. Then:

1. The status is the expected one. Else, below the floor,
   `pull answered <s> for a position below the retention floor <F>`, and otherwise
   `pull answered <s>, expected <e>`.
2. `resync-required`: `current` has the peer's history and the expected revision, else
   `pull reports resync-required with current <c>, expected <C>`. How a `current` of another
   history is rendered is each witness's own (Rust adds ` (history <h>)`; TypeScript writes the
   revision alone). The cursor's position is still
   `before`, else `the cursor moved after resync-required`. Check the calls (below). The step
   ends.
3. `ok`: the position has `before`'s history, else `the pull moved the cursor to another history`.
   Let p be its revision. p lies in [`before`, `end`], else
   `the pull's position <p> lies outside [<before>, <end>]`; and p > `before` unless
   `before` = `end`, else `the pull from <before> made no progress toward <end>`.
4. The records' revisions are those of the model records in (`before`, p], in order, else
   `the pull's records are at [<revisions>], expected [<revisions>]`. Each record equals the model
   record, head and both id lists, else `the pull's record at revision <r> differs from its
   commit`.
5. The deltas are ascending by id and distinct, else
   `the pull's deltas are not ascending by id and distinct`.
6. Their ids are exactly the ids in some `added` of the model records in (`before`, p] that the
   bookkeeping holds now, else `the pull delivered [<ids>], expected [<ids>]`.
7. Each delta is the appearance the peer holds (same `sig`, claims that recompute to its id), else
   `the pull delivered <id> as another appearance`. Its arrival record names its id and equals the
   bookkeeping's, field by field, else `the pull delivered <id> with another arrival record`.
8. The cursor's position is the pull's, else
   `the cursor stands at <r>, not at the pull's position <p>`.
9. Check the calls (below).
10. Apply the pull to the mirror by the rule of SPEC-18 §4.6: for each record in order, delete each
    id of `removed`; then for each id of `added`, set it to its delivered delta, or delete it when
    none was delivered. With `once`, the step's pulls are done; otherwise they are done when
    p = `end`.

**After the pulls of an ok step:** let s be where the cursor stands.

- With `once`: s is the revision `position` names, else `the pull stands at <s>, expected <P>`.

11. The revisions read equal those `records` names, in order, else
    `the pulls read the records at [<revisions>], expected [<revisions>]`.
12. The ids delivered, distinct and ascending, equal `delivered`, else
    `the pulls delivered [<ids>], expected [<ids>]`.
13. With `pulls`: the count equals it, else `the follower took <k> pulls, expected <n>`.
14. **The guarantee.** When s is short of the peer's revision (only with `once`): for every id that
    no model record after s names, the mirror and the bookkeeping agree (both lack it, or both hold
    it with equal arrival records), else
    `after the pull to <s> the follower's mirror differs from the holdings at <id>`. The runner
    commits nothing during a pull, so the holdings at s of such an id are its holdings now. When
    s is the peer's revision: the mirror's ids equal the bookkeeping's, else
    `the follower's mirror holds [<ids>], and the peer holds [<ids>]`; and each arrival record is
    equal, else `the follower's mirror holds <id> with another arrival record`. When checks 1 to
    10 pass, this cannot fail: SPEC-18 §4.6 proves it. The runner keeps it as the guarantee's own
    check; a witness confirms it is live by breaking its runner's apply rule (it then goes red).

**The calls.** Wrap the peer handle given to `follow` so that every call through it, and through
every snapshot it returns, is logged with its arguments (for `read`, the snapshot's revision and
history; log the call when it is made, so a call no one waits for is seen, and so is a call
that then refuses). Write each call as
text: `read`; `changes(<from>, <to>)`, with `none` for an absent `to`; `get [<ids>]` and
`arrivals [<ids>]`, each id cut to 12 characters, joined by spaces; `release`; any other operation
by its name. Walk the log of one pull against the contract:

- After the cursor answered `resync-required` in an earlier pull: no call at all.
- Otherwise the first call is `read`. Let r′ and h′ be its snapshot's revision and history.
- When h′ is `before`'s history and r′ > `before`: the next call is `changes(<before>, <r′>)`.
  When it answered `ok` and its records add ids, the next calls are `get` and then `arrivals` of
  every id in some record's `added`, distinct, ascending.
- The next call is `release`, and it is the last.

So the history is compared before any feed call, a position past the snapshot or at it makes no
feed call, a pull reads one page with an explicit `to`, and a page that adds nothing makes no
`get`. A call that differs from the one the walk asks for fails with
`pull made the call <actual> where the contract asks for <expected>`; a missing call with
`pull made no call where the contract asks for <expected>`; a call after the last with
`pull made the call <actual> after its last call`.

The runner never commits while a pull runs, so a pull that starts again on a new snapshot after
`snapshot-moved` is never seen here. Each witness tests that itself (§10.6).

**Messages.** As in §3.9 and §9.3, the fixed words of each message of §10 are normative, and a
witness MAY put a step locator before them. How a value inside a message is rendered is each
witness's own. The revisions in the table below are the memory store's.

### 10.4 The runs each witness makes

Run every case against the reference store, each field of a case's `store` replacing the run's:

1. As built by default.
2. With pages of one record.
3. Keeping two records.
4. Keeping two records, with pages of one record.
5. Revisions times 3, with pages of one record (the scaled store of §8, "Stores that must pass").
6. Revisions times 2, keeping two records.

Both witnesses run all six. A witness whose store has no page limit runs 1, 3 and 6. Every run
passes every case of the file and skips nothing; each witness asserts that the cases it ran are
exactly the file's, by name.

### 10.5 What the cases hold

- Nothing new: a pull at the peer's own revision, twice (`nothing-new`).
- One append (`one-append`); three records in one page, one with three deltas that arrive in the
  reverse of id order (`several-records-in-one-page`).
- Pages of one: a step takes one pull per record; an id added, purged and added again across the
  pulls of one step (`pages-of-one`).
- A head-only commit: a record with no ids and no `get` (`a-head-only-commit`).
- A purge of a held id (`a-purge-of-a-held-id`).
- Added then purged inside one page: no bytes (`add-then-purge-in-one-page`).
- Added, purged and added again inside one page: delivered once, with its new arrival record
  (`add-purge-add-in-one-page`); the same across pulls, and a purge and a re-add between two
  pulls (`add-purge-add-across-pulls`).
- A purge whose bytes another peer holds, the other peer's purge that removes them, and a purge
  that settles a debt and writes no record; no follower gets bytes
  (`a-purge-held-by-another-peer-and-a-settled-debt`).
- Two peers that commit in turn and share bytes: each follower reads its own peer only
  (`two-peers`).
- A store that keeps one record: `resync-required`, twice (`retention-too-short`).
- A position two revisions past the peer (`a-position-from-the-future`); a position with another
  peer's history and a revision the peer has (`another-peers-history`); a pull after a resync,
  once the peer has passed the position, answers the first `current` again
  (`pull-after-resync`).
- A follower started after four commits, whose later commits purge an id held before the follow
  and add it again (`a-follower-started-mid-history`).
- Single pulls with commits between them, each case with pages of one and every record kept:
  - an id added, purged and added again; the first pull delivers it; it is purged once more; the
    third pull reads the second add and delivers nothing (`a-purge-between-single-pulls`);
  - an append between single pulls (`an-append-between-single-pulls`);
  - a purge of an id the follower already mirrors (`a-purge-of-a-mirrored-id-between-single-pulls`);
  - a purge and a re-add of a delivered id, read one record at a time
    (`a-re-add-between-single-pulls`).

- **The follow step and the document.** A `positionOf` of another history (`the position's history
  is not its snapshot's`) and of another revision (`the position is of revision 2, expected 1`);
  a cursor that ignores the position it is given (`a new cursor stands at 1, …`); following that

- **Every check has a row.** Remove a check of §10.2 or §10.3 from the runner and its row goes red.

  `follow refused with invalid-request`. An unknown follower on a store with no feed fails with
  `the vector uses follower g before following`. The case `store` defects, a factory that cannot
  build a case's store (skipped, `store`), and one that fails otherwise (that case fails, the
  others run) each have a rail. The call log records a call that refuses.
- **The cursor's own rules.** A malformed position is refused `invalid-request` with no store call;
  `parsePosition` reads `3.0` as 3 and refuses a local history, another shape, an empty history and
  `1.5`. After `resync-required` a pull answers the same with no store call, also after commits;
  `current` is the snapshot's position, also when the store's answer names another revision. On
  `snapshot-moved` a pull starts again (the calls `read`, `changes`, `get`, `release`, then again
  with `arrivals`), at most four snapshots, each released; a `read()` that itself answers
  `snapshot-moved` counts the same (three, and the fourth snapshot answers; four, and it passes
  up). An error releases the snapshot and does not move the cursor. A page with no progress and
  one whose `through` is the asked `to` plus 5 fail the pull with a store fault, `no-progress` or
  `past-the-bound`, not a store refusal and not a panic; `get` and `arrivals` that disagree fail
  with `mismatched-answers`. A `get` and an `arrivals` that both answer one more id, in order and
  in agreement, fail with `unasked-ids`, deliver nothing, and leave the cursor usable (SPEC-18
  §4.13 reading 74). **A fault is found before the page is judged:** the same two faulty pages, each also
  carrying a record that adds an id, fail with the calls `read`, `changes`, `release` and no
  `get`. The matching rail of §9.7 gives `checkFresh` faulty pages that add a touching id; it must
  fail with a store fault, not answer `stale`. Two pulls started together run one after the other. A purge whose bytes another peer
  holds delivers no bytes. A read and a fetched scope carry their snapshot's position, and a
  reactor follows from it.
- **A fuzz against brute force**, with a fixed seed, at least 2,000 sequences: a store kept whole or
  keeping one to four records, with whole pages or pages of one to three records; two peers that
  share a corpus (debts across peers); random appends, head-only commits and purges on both; and
  single pulls of a follower of the first peer, which starts from a full read and starts again
  from a new read after a second `resync-required`. Half the followers start from one snapshot.
  The other half start as SPEC-18 §4.6 "How a full mirror starts" says: the position of a
  snapshot first, then an export that reads each id's bytes and its arrival record each on its
  own later snapshot, with appends, purges and re-adds on both peers landing between them (an id
  the peer no longer held when its arrival was asked has none). Each pull equals the model's: status
  (`resync-required` exactly below the floor, and after it), position, records and delivered ids
  with arrival records. After each ok pull to p, the mirror equals the holdings at p for every id
  no later record names; at each quiet point it equals the holdings, from either start. A mirror
  that ignores `removed` misses them; one that applies a page's removals before its deltas does
  not, and neither does one that keeps an added id that came with no bytes. The TypeScript fuzz
  asserts that some export starts were skewed (a mirror not equal to the holdings at p0) and some
  entries had no arrival record.
- **The cost rails**, timed from outside as in §3.9.9 (N from 256, doubling until the run takes
  50 ms; the run at N the fastest of five; the run at 8N the fastest of three, stopping at the
  first under the bound; the ratio below 24). A run is N pulls, each by a new cursor at one
  position, each reading the same page of 16 records:
  1. beside N held deltas (and at 8N, 8N), all appended before the position;
  2. after N records before the position (N head-only commits).

  A pull that reads the holdings or the earlier records costs N per call, and the total scales by
  about 64. The TypeScript witness measured ratios of 9 to 10 for both.

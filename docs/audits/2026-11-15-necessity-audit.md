# What in Rhizomatic is necessary?

Independent necessity audit · November 15, 2026

Rhizomatic `51ec0d596ff15f83bdd28235245eb644b3dd0ca2`; consumer inspection at Loam `0b78ccde7882862f2c2b3bfb45097de345f3bf0a`. The audit changes no repository source and publishes no GitHub comments. Recommendations below distinguish behavior-preserving cuts from deliberate reductions in the promised API.

**Verdict:** keep the portable rules and their independent witnesses. Make storage, maintained views, federation and command protocols explicit optional layers. Shrink generated representations and the machinery used to certify them before removing behavior. The new store is mostly an answer to real operational requirements; its packaging and the size of its contract are much less justified.

## 2. Verdicts and the smallest version of each promise

| Area | Verdict | Promise and smallest version | What can go; what would break |
| --- | --- | --- | --- |
| Core rules | **KEEP** | Content-derived identity, strict canonical codecs/signatures, union merge, explicit suppression, deterministic algebra, schema selection and resolution. A pure package with no store, endpoint or host transport requirement. | Remove compatibility barrels and make principal/derivation/evidence support explicit imports where practical. Preserve all existing canonical bytes and operator meaning. L0/L1 vectors, CRDT properties, principal vectors and cross-witness canonical outputs are the loss detectors. |
| Store runtime | **SPLIT OUT** | An indexed, snapshot-consistent peer store with atomic append, purge reports/posture gating, history/revision and a bounded change feed; anchored reads depend on it. Consolidate repeated prose and stop treating exact diagnostic sentences as substrate law. Keep malformed-input rejection, failure classification, ownership, cost bounds and all erasure checks. |
| Federation and peer journals | **SPLIT OUT** | Pure transfer/admission planning plus explicit durable host capabilities: identity, admission, atomic head agreement, refusals/exclusions and purge obligations. | The store arc replaces whole-holdings checkpoint images and duplicated row/arrival storage, not admission or erasure policy. Retire the old whole-image serving path only after the store-backed journal keeps the same replay/CAS/erasure guarantees. Old Peer/HTTP demo convenience APIs need not enter the rules-only package. |

“Split out” first means explicit module/subpath and build boundaries in the same repository. It does not require fourteen new npm packages, fourteen release schedules or a repository split. A separate conformance package is justified because its audience and dependencies are different. Rust can use opt-in features or a workspace test crate; the Rust crate currently has `publish = false`.

## 3. The core is necessary; its current perimeter is negotiable

The smallest rules library is smaller in concept than the brief’s directory sum: format and identity; merge and suppression; typed operators; schema/reading representation and resolution. Anchoring and resource budgets support execution. Principal association, derivation hosts, portable envelopes and command-program validation are useful extensions with consumers, rather than prerequisites for storing a signed delta or evaluating a simple term.

I would preserve the implemented algebra during this audit. There is no evidence here that deleting an operator, principal semantics or derivation ABI would retain the same expressiveness and provenance promises. I also would not declare the core “already minimal” from its line count. For example, [implementations/ts/src/schema/command-program.ts](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/src/schema/command-program.ts) is protocol-specific validation inside a nominal core boundary. The useful cut is the dependency boundary, not a smaller line budget.

Existing [tools/check-package-graph.mjs](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/tools/check-package-graph.mjs) already checks 127 TS modules, 641 local imports and 14 internal owners. Reuse that work to enforce a pure entry point. The present npm exports are only the aggregate root and a Node adapter; directory boundaries alone do not give consumers an independently importable core.

## 4. Store claims tested against code

### Four slice-3 abilities: real need versus current use

| Ability | Observed consumer today | Slice-5 replacement | Necessity judgment |
| --- | --- | --- | --- |
| Feed | No production Loam import of the new store API. Existing catchUp and refreshImpl are real runtime paths. | Loam ingest.ts: catchUp rereads admitted inventory; refreshImpl compares a journal head. | Keep in the store: ordered additions/removals and resync are the substrate for bounded cross-process catch-up. |
| Freshness | No Loam checkFresh import. Loam does check durableCurrent and keys caches on a reactor/derived revision. | Capture-based scoped invalidation; validity windows; external state handled separately. | Optional optimization/correctness helper. A consumer can reread each bounded scope, or invalidate conservatively on every revision, without changing read answers. |
| Cursor | No Loam followFeed import. The catch-up consumer exists. | One snapshot and one feed page, coherent rows/arrivals, serial progress and terminal resync. | Keep as a small optional adapter over the feed rather than duplicating the delicate pager in each host. It is not a second storage capability. |
| Held views | No Loam StoreViews import. Loam does use Reactor.register, materializedView, subscribe and advanceTime. | StoreViews plus host callbacks/epochs replaces maintained materializations. | A real replacement target, but not a dependency of the rules or of a plain anchored read. Keep optional and shrink the notification contract before adoption. |

Consumer evidence is pinned source, not an inference from the plan: [Loam catchUp / refreshImpl](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/ingest.ts#L281), [maintained reads and subscribers](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/reads.ts#L610), [durableCurrent](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/gateway.ts#L560), [registration](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/lifecycle.ts#L196). The inventory searched all production `loam/src` imports; it does not establish that there are no other external users.

There is a sequencing issue here: the §12 amendment says slice 5 depends on the feed and nothing else in the former slice 3, but the work subsequently built freshness, a cursor and a sophisticated holder before the durable consumer moved. Those helpers have uses; their existence does not establish that every one had to precede the first real store trial. Stop widening that prerequisite chain.

### A smaller held-view promise is available

The current holder promises more than “keep a bounded set of views current”: it retains a previous refresh baseline, returns `before` payloads, suppresses changes that cancel before refresh, and coordinates `hold.from`, `changed` and `evicted`. That creates a second payload lifetime, a baseline inverted index and several erasure/eviction rules.

**Recommended contract reduction:** current bytes plus dirty/invalidation notifications carrying the latest value, with explicit eviction. Drop retained `before` payloads. Permit a notification after a value changes and changes back; subscribers may suppress duplicates. Loam’s current sink already resolves current state and compares its own `lastHex`; it consumes `changedProps`, not historical before/after payloads. The new StoreViews integration must still define property hints or conservatively invalidate them.

The promise surrendered is exact refresh-to-refresh before/after reporting and cancellation suppression, not current view correctness. The host-copy model and fixtures such as `a-new-view-that-changes-before-the-refresh`, the baseline-release tests and tests for return-to-baseline notifications must change explicitly. Preserve the fresh-read equivalence fuzz, coherent single-snapshot passes, time/epoch invalidation, eviction notification and erasure tests. This is a deliberate API redesign, not part of the lossless first cut. Do not replace deleted payloads with retained digests if that weakens the existing erasure information boundary.

### Production code carries intentional failures

**Concrete finding:** [ViewQuirks](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/src/reactor/store-views.ts#L133) says the controls are not part of the package surface, yet the public [StoreViews constructor](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/src/reactor/store-views.ts#L361) accepts them as its third argument. It includes `keepPurgedBaseline`, `ignoreRemoved`, `advanceOnFailure` and other deliberately invalid choices. Rust exposes [StoreViews::with_quirk](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/rust/src/store_views.rs#L324) without a test-only compilation guard; hiding documentation does not make it private.

An independent probe using only the built root exports created a target and a bystander, captured and held both, purged the target and refreshed. Default behavior reported an unproven memory purge, stale capture, removal in the cursor, no purged bytes delivered, `before: null` and unchanged bystander bytes. Calling `new StoreViews(peer, {}, {keepPurgedBaseline: true})` made the refreshed `before` contain the secret. This is an unnecessary public failure mode, not a defect observed in the default algorithm. Keep the adversarial tests by generating mutants in temporary test builds or behind a test-only build boundary.

### Erasure remains the constraint on every cut

The new memory store is explicitly `unprovable` and correctly refuses a proven posture. The proven SQLite store is still a later slice. The existing consumer’s durable erasure work cannot be replaced by “row no longer queries” or by a successful memory test.

- Keep permanent refusal/exclusion, outstanding purge debt, multi-peer holdings and target/bystander checks. [Old journal bytes keep debt owed](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/test/peer-permanent-journal-api.test.ts#L683) is especially important when splitting the journal.
- Before retiring the old durable path, carry over [Loam physical-surface tests](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/test/store/erasure-at-rest.test.ts#L53): database plaintext, WAL truncation, crash-persistent debt, busy readers, unrelated targets, temporary files and mirror healing. I inspected these tests as consumer requirements; I did not rerun Loam’s suite.
- Treat a live snapshot, follower mirror, held baseline and caller-owned result as separate payload lifetimes. A failed held-view pass is not an erasure. Keep the two-sided [purge and failed-pass checks](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/test/store-views.test.ts#L1128) and explicitly account for host copies.
- Keep feed identifiers separate from payload absence. The spec already allows purged IDs to remain in the feed and documents the guessing risk. A bounded-retention default and an honest feed surface report are owed by slice 4; this audit does not weaken that boundary.
- The revision-range follow-up is real: a wrapped snapshot with revision 9,007,199,254,740,992 was accepted by both StoreReactor.read and fetch. The guarded helpers refuse such revisions. Add the common range check before a read can publish an unusable position; clarify attempts as attempts, including read() refusals. This is the known \#83 follow-up, not a new discovery.

## 5. Generated bytes: a measured behavior-preserving cut

Both materialization files are generated by [implementations/ts/tools/gen-materialization-command-vectors.ts](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/tools/gen-materialization-command-vectors.ts). Commands contains 25 positive cases, 129 negative cases and 15 result-rejection cases; lifecycle contains 136 steps. These are substantial tests, not evidence of 22 MB of independently authored semantics. In lifecycle, `expected.controlHex` and `initialControl.hex` alone account for about 9.17 million string bytes. Nested bodies and signed appearances repeat the same data again.

I ran the round and materialization generators and reproduced all three original files byte for byte. I also tested a simple JSON dictionary that replaces repeated strings of at least 96 characters with references. Expanding it reproduced the exact original JSON bytes, not merely an equal parsed object:

| Fixture | Current bytes | Pooled bytes | Saved |
| --- | --- | --- | --- |
| materialization/lifecycle.json | 16,031,883 | 6,086,858 | 9,945,025 |
| materialization/commands.json | 6,091,953 | 2,950,165 | 3,141,788 |
| store/rounds.json | 2,537,343 | 1,344,295 | 1,193,048 |
| **Total** | 24,661,179 | 10,381,318 | **14,279,861** |

This single experiment removes 14,279,861 bytes, or 31.1% of the tracked tree, with every test case and expected canonical output unchanged. It is a feasibility measurement, not a committed new vector format. A production version should share named appearances/control images as well as blobs, keep small readable expected outcomes, version the pool format, and test the expander independently. Publish an expanded language-neutral corpus as an artifact for third-party witnesses.

`rounds.json` comes from [implementations/ts/tools/store-round-vectors.ts](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/tools/store-round-vectors.ts) and a [generator cross-check](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/ts/tools/gen-store-round-vectors.ts) against whole-memory anchored reads. A seed alone is insufficient: it describes generated inputs, not a fixed expected result. Keep the independent list model, named corner cases, canonical expectations/digests and a pinned generator; expand larger stress corpora during CI. The round/view models reuse native evaluation, so their independence tests storage traversal and invalidation, not an independently implemented evaluator. Existing algebra vectors and Rust canonical comparisons still matter.

### The 7.6 MB inventories have actual readers

TS [tools/command-inventory.mjs](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/tools/command-inventory.mjs) computes exports through the compiler; Rust’s AST extractor feeds [tools/check-rust-command-boundaries.mjs](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/tools/check-rust-command-boundaries.mjs) and [tools/enrich-command-api.mjs](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/tools/enrich-command-api.mjs). The package graph, boundary checks, inventory negative tests and precheck consume these reports. They should not simply be deleted.

Much of their prose is deterministically generated from [contracts/command/API.json](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/contracts/command/API.json) and owner rules. Of 4,002 TS entries, 1,993 are classified as compatibility re-exports. Keep a compact, reviewed manifest of the supported public surface and any non-derived classification overrides, plus the source boundary rules. Compute expanded members, dependency paths and explanatory prose into temporary reports. Preserve rejection of missing/new/unclassified exports and illegal owner/host imports; deriving “approved” classifications automatically from live code would erase that check. The current inventory also does not freeze complete TypeScript type signatures; its size must not be mistaken for a full API compatibility proof.

## 6. Federation, commands and the witness trade

Loam uses [OrdinaryJournalPeer](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/peer-admission.ts#L1) in real boot, receive and erase paths, and its memory/SQLite/mirror drivers implement `DurableOrdinaryJournalStore`. The new store replaces that physical adapter and the large embedded holdings/arrivals image. It must retain the pure admission planner, signed identity checks, atomic compare-and-set, exclusions, ordered refusals and outstanding erasure obligations. A Merkle root is not a replacement for the exclusion/debt state or for physical removal.

The current [store journal proposal](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/spec/18-store.PROPOSAL.md#L926) promises tail-bounded open and verification on use/fsck. Slice 4 still owes a check that missing index entries cannot silently omit data, coherent commit ordering, durable history identities and snapshot-aware erasure reports. Those are reasons to pilot a real consumer before broadening the store architecture; they are not reasons to weaken erasure or drop the old rails early.

The blanket “weak consumer link” diagnosis for commands is too broad. [Loam operator commands](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/operator-command.ts#L68) boots CommandEndpoint for retain/evaluate; [the CLI door](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/cli/command.ts#L83) reaches it. [Portable reads](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/portable-read.ts#L264) invokes MaterializationEndpoint and decodes canonical evidence, reached through [the query door](https://github.com/bombadil-labs/loam/blob/0b78ccde7882862f2c2b3bfb45097de345f3bf0a/src/gateway/portable-door.ts#L292). Its installed verbs are gather and resolve. I found no production Loam control-store or install/reconcile/pin/retire invocation. Keep the batch protocol; move the maintained-control protocol out of the default path.

The roughly 7,700 Rust lines versus 4,400 TS lines are not by themselves evidence of removable behavior. Rust uses explicit JSON value decoding, closed-shape validation, distinct error/value types and synchronous trait adapters where TS uses compact structural types. For example, materialization_source.rs is 1,093 lines, including a 219-line test section counted as source. Its codecs, lifecycle and source validation are not a mechanical one-to-one translation. The crate is a conformance witness and WASM demo backend, not a separately published product. First remove protocol duplication at the boundary, then judge local implementations.

**Recommended witness policy:** keep two independent implementations for a stable/released capability and canonical wire behavior. Permit an experimental slice or consumer spike to change in TS before asking Rust to implement the settled contract from documents. Rust validation must finish before the capability is advertised as conformant. This changes the current lockstep working agreement and should be recorded explicitly; this audit has not silently changed it. It saves repeated implementation/review churn without surrendering the independent-witness check at acceptance.

Elixir’s [implementations/elixir/FINDINGS.md](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/elixir/FINDINGS.md) documents concrete pack-format gaps; Haskell’s [implementations/haskell/FINDINGS.md](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/implementations/haskell/FINDINGS.md) documents independent number/type behavior and honestly says it was not a clean-room experiment. Their current manifests, check-all discovery and CI jobs settle whether they run. Keep them at L0 and avoid charging command-only edits for unrelated language setup when dependency-aware CI can safely skip it.

## 7. Documentation and generated site output

PROGRESS still contains old July “RESUME HERE” instructions. AGENTS already says they are history. Archive that document and replace the landing status with one current roadmap. CHANGELOG is valuable release history, but Unreleased simultaneously says the reactor does not yet use the store and describes slices 2 and 3; it also says Rust “follows” after the implementation is complete. Rewrite Unreleased as the current cumulative state. Archiving history improves comprehension; moving a file to another directory does not save its bytes.

The drift reaches the overview too: its final portable-evidence paragraph says only M1 codecs are implemented, although AGENTS and the actual command/materialization code describe completed M0–M4 work. Update present-tense summaries together; keep milestone handoff notes explicitly historical.

The tracked WASM plus two bundles occupy 1,552,253 bytes. [CI](https://github.com/bombadil-labs/rhizomatic/blob/51ec0d596ff15f83bdd28235245eb644b3dd0ca2/.github/workflows/ci.yml#L103) rebuilds/diffs the JS bundles, but the Rust job builds and uploads a WASM artifact rather than comparing it with the tracked docs binary. A deployment build should take all three from one source revision. Keep docs HTML/CSS/source, and verify the deployed tour/playground before removing their checked-in assets.

The working agreement’s Markdown-only shortcut applies to normative spec Markdown too. Restrict the shortcut to ordinary documentation/history; a spec change should require corresponding vector review and relevant gates. For comments, preserve the short reason that prevents a canonicalization or erasure regression. Remove dead narration and comments contradicted by public declarations, such as the claim that ViewQuirks is outside the package surface.

Do not use the large byte cut as a claim that engineering complexity disappeared. Fixture pooling primarily reduces checkout/review/storage noise. Moving optional protocols and simplifying unneeded notification semantics reduce the promises every library consumer and maintainer must carry.

## 9. Slice-3 reading map: all 102

This is a traceability map, not a claim that each paragraph has an independent test or a formal proof. Links name the focused TS test, shared-vector runner, source/type property or host obligation I found. Rust counterparts are store_feed, store_feed_rules, store_freshness, store_follow, store_views and store_rounds in implementations/rust/tests.
